# 공개 전환 보안 점검 (2026-09-29)

| 항목 | 확인 결과 |
| --- | --- |
| 공개 범위 | EC2 보안 그룹은 TCP 80·443을 공개하고 SSH 22는 기존 단일 IPv4 `/32`로 제한한다. DB·스토리지·Django·Spring 직접 포트는 Tailscale 주소 또는 루프백에만 바인딩된다. |
| HTTPS | `yeogiljido.com`의 DNS가 EIP `13.124.108.133`을 반환한다. Caddy가 EC2 사설 주소에만 바인딩돼 Tailscale 443과 공존한다. Let's Encrypt 인증서 발급 로그 및 외부 `curl` 인증서 검증값 0을 확인했다. HTTP는 HTTPS로 308 이동한다. |

| SSH | 비밀번호·키보드 입력 인증은 꺼져 있고 공개키 인증만 켜져 있다. `PermitRootLogin without-password`이므로 루트 공개키 로그인은 여전히 가능하다. 루트·ubuntu 모두 authorized_keys가 있다. |
| 운영체제 | 업그레이드 가능 패키지 42개, 재시작 필요 표시가 있다. `unattended-upgrades`는 활성이다. 패키지 업그레이드와 재부팅은 서비스 중단 검증을 동반하므로 이번 공개 연결에서 실행하지 않았다. |

## 남은 위험과 다음 조치

1. **로그인 요청 제한의 IP 식별 — 우선 수정:** Spring `PublicWriteRateLimitFilter`는 `request.getRemoteAddr()`를 키로 쓰고, 공개 요청은 Caddy·Nginx를 거쳐 동일한 게이트웨이 컨테이너에서 Spring에 전달된다. Spring에 신뢰된 프록시의 원래 접속자 주소를 복원하는 설정은 없다. 코드·라우팅 기준으로 공개 이용자들의 요청이 한 IP 한도에 합쳐지는 결함이다. 현재 로그인 20회/분, 가입 5회/분이며 실제 차단 실험은 이용자 로그인에 영향을 줄 수 있어 실행하지 않았다. Caddy가 외부 `X-Forwarded-For`를 기본적으로 무시하는 점을 활용하되, Nginx와 Spring이 신뢰할 프록시만 명시한 뒤 서로 다른 IP·위조 헤더·직접 Tailscale 접속 회귀 테스트를 통과시켜야 한다.
2. **공개 주소 소셜 로그인 — 우선 수정:** 운영 Spring의 `SOCIAL_PUBLIC_BASE_URL`과 공급자 개발자 콘솔 콜백은 여전히 Tailscale 주소다. 외부 `https://yeogiljido.com/spring/api/auth/social/google/start` 호출에서 302 `Location`이 기존 `.ts.net` 주소인 것을 확인했다. 기존 앱 로그인을 유지하려고 변경하지 않았다. 새 주소의 OAuth 왕복 테스트 전에는 공개 웹 로그인 완료를 주장하지 않는다.
3. **SSH 루트 로그인:** 운영 접속은 `ubuntu` 계정을 사용한다. 루트 직접 로그인 필요성을 확인하고 `PermitRootLogin no` 적용·접속 회귀 확인을 계획한다.
4. **운영체제 보안 업데이트:** 적용 대상과 재부팅 영향, 백업·복구 경로를 확인한 뒤 점검 시간을 잡아 업데이트한다. 현재 서비스 가동 중 즉시 재부팅하지 않는다.
5. **규모가 커진 뒤의 방어:** 현재 메모리 기반 인증 제한은 단일 Spring 프로세스에만 적용된다. 인스턴스 확장 전에 공유 저장소 또는 엣지 제한으로 변경하고, 4xx/5xx 및 인증 실패 급증 경보를 추가한다.

이 점검은 포트·선정된 API·설정의 표본 검증이다. 전체 취약점 진단이나 침투 테스트 완료를 뜻하지 않는다.

## 점검 결론

공개 HTTPS와 비인증 관리자 접근 차단은 확인됐다. 공개 웹의 로그인은 아직 출시 준비가 되지 않았고, 로그인 요청 제한은 프록시 뒤에서 사용자별로 작동하지 않는다. 두 항목을 먼저 수정·회귀 검증한 뒤 새 도메인의 실제 소셜 로그인 왕복을 확인해야 한다. 루트 SSH 로그인 제한과 운영체제 업데이트는 별도 접속·복구 검증을 포함해 진행한다. 이번 점검 중 운영 설정·데이터·서비스를 변경하지 않았다.
