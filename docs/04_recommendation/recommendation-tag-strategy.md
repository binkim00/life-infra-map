# 추천 가치 태그 전략

## 1. 문서 목적

이 문서는 상황 기반 장소 추천 서비스에서 추천 가치 태그를 어떻게 정의하고, 확보하고, 검증하고, 추천 점수에 반영할지 정리하기 위한 문서입니다.

본 서비스는 단순히 지도 API 검색 결과를 보여주는 것이 아니라, 장소별 태그의 출처와 검증 상태를 관리하여 사용자의 상황에 더 적합한 장소를 추천하는 것을 목표로 합니다.

현재 구현에서는 흡연구역 DB 기반 추천, 카페 태그 fixture, 관광지 블로그 기반 후보 태그 생성까지 진행되었습니다.

---

## 2. 태그 구분

### 2.1 카테고리/필터용 태그

장소의 종류를 구분하거나 기본 필터에 사용하는 태그입니다.

예시:

- 카페
- 공원
- 흡연구역
- 공중화장실
- 주차장
- 무료 와이파이
- 관광지
- 해수욕장

### 2.2 추천 가치 태그

사용자의 상황과 직접 연결되어 추천 품질을 결정하는 태그입니다.

예시:

- 혼자 이용 좋음
- 오래 머물기 좋음
- 조용함
- 노트북 작업 가능
- 콘센트 있음
- 와이파이 있음
- 분위기 좋음
- 산책하기 좋음
- 힐링하기 좋음
- 전망 좋음
- 야경 보기 좋음
- 사진 찍기 좋음
- 드라이브 목적지

### 2.3 상태/주의 태그

추천 점수 보정이나 사용자 안내에 사용하는 태그입니다.

예시:

- 좌석 확인 필요
- 콘센트 확인 필요
- 와이파이 확인 필요
- 운영 정보 확인 필요
- 위치 확인 필요
- 테이크아웃 가능성
- 폐업 여부 확인 필요
- 후보 태그 검수 필요

---

## 3. 태그 저장 기준

모든 지도 API 검색 결과를 DB에 저장하지 않습니다.

DB 저장 대상은 다음과 같습니다.

- 자체 수집 후 정제한 데이터
- Django fixture로 변환한 데이터
- 팀이 직접 확인한 장소
- 사용자가 저장한 장소
- 사용자 또는 관리자가 검증한 장소

지도 API 검색 결과는 기본적으로 DB에 저장하지 않고, 추천 시점에 임시 태그를 부여한 후보 장소로만 사용합니다.

단, 카페처럼 공공데이터만으로 추천 가치 태그 확보가 어려운 경우에는 지도 API 검색 결과와 블로그 검색 결과를 활용해 후보 데이터를 만들 수 있습니다. 이 경우에도 API 제공사의 저장 정책을 확인하기 전까지 대량 저장 방식은 확정하지 않습니다.

---

## 4. 태그 출처

| 출처 | 설명 | 현재 사용 예시 |
|---|---|---|
| category_rule | 카테고리 기반 자동 태그 | 흡연구역 → 흡연, 공원 → 산책 |
| field_rule | 원본 컬럼 기반 태그 | 주차장 운영시간, 공원 보유시설 |
| keyword_rule | 장소명/설명 키워드 기반 추론 태그 | 전망대 → 전망 후보 |
| blog_search | 블로그 검색 결과 기반 후보 태그 | 카페/관광지 후보 태그 |
| ai_suggested | AI가 제안한 후보 태그 | 자연어 입력 분석, 후보 태그 제안 |
| external_data | 공공데이터 원본에서 확인 가능한 태그 | 공중화장실 편의시설, 무료 와이파이 |
| team_checked | 팀이 직접 확인한 태그 | 팀 시드 데이터 |
| admin_checked | 관리자 또는 팀 검수 태그 | 후보 태그 승인 |
| user_verified | 사용자 검증 기반 태그 | 운영 중 검증 기능 |

---

## 5. 태그 상태

| 상태 | 설명 | 추천 반영 |
|---|---|---|
| confirmed | 확인 근거가 있어 추천 점수에 강하게 반영 가능한 태그 | 강하게 반영 |
| candidate | 가능성은 있지만 아직 확정되지 않은 후보 태그 | 약하게 반영 |
| needs_verification | 확인이 필요한 태그 | 안내 또는 감점 |
| rejected | 검증 결과 맞지 않는 것으로 판단된 태그 | 제외 또는 강한 감점 |

현재 블로그 검색 결과 기반 카페/관광지 태그는 `candidate` 상태로 보는 것이 안전합니다.

## 6. 데이터 유형별 태그 전략

### 6.1 흡연구역

- 현재 DB 조회 방식으로 추천에 연결되었습니다.
- 기본 태그는 `흡연`, `흡연구역`, `생활불편해결`입니다.
- 실내/실외/개방형/폐쇄형 정보는 원본 컬럼이 명확할 때만 부여합니다.
- 사용자에게는 거리와 데이터 출처를 함께 보여줍니다.

### 6.2 카페

- 카페는 공공데이터만으로 조용함, 콘센트, 노트북 작업 가능 여부를 확정하기 어렵습니다.
- 지도 API와 블로그 검색 결과를 활용해 후보 태그를 수집했습니다.
- 현재 카페 태그 데이터는 Django fixture 형태로 준비되어 있습니다.
- `조용함`, `노트북 작업 가능`, `혼자 이용 좋음`, `분위기 좋음` 등은 후보 태그와 검증 태그를 구분해서 관리합니다.
- 유명 저가형·테이크아웃 중심 브랜드는 무조건 제외하지 않고, 필터링 또는 주의 태그 대상으로 관리합니다.

### 6.3 관광지/해수욕장

- 관광지와 해수욕장은 산책, 힐링, 전망, 야경, 드라이브 목적지 후보로 활용할 수 있습니다.
- 블로그 검색 결과 기반 태그 후보 생성 스크립트를 통해 후보 태그 JSON을 만들었습니다.
- 블로그 기반 태그는 확정 정보가 아니므로 `candidate` 상태로 관리합니다.
- 야경, 사진, 힐링, 전망 같은 태그는 검수 전까지 약하게 반영합니다.

### 6.4 주차장

- 장소명, 주소, 좌표, 운영시간, 요금 정보, 주차장 구분을 우선 정제합니다.
- `주차 가능`, `공영`, `무료`, `유료`, `야간 이용 가능 후보` 등은 원본 컬럼이 명확할 때만 부여합니다.
- 실시간 주차 가능 대수는 초기 구현 범위에 포함하지 않습니다.

### 6.5 공공와이파이/공중화장실/도시공원

- 공공데이터 원본 컬럼에서 확인 가능한 정보는 `field_rule` 또는 `external_data` 태그로 관리합니다.
- 무료 와이파이 데이터만으로 `노트북 작업 가능`, `콘센트 있음`, `조용함`을 확정하지 않습니다.
- 도시공원 데이터만으로 `야경 좋음`, `데이트 좋음`, `조용함`을 확정하지 않습니다.

## 7. AI 활용 방식

AI는 실제 장소 정보를 생성하거나 태그를 확정하지 않습니다.

AI 활용 범위는 다음으로 제한합니다.

- 사용자 자연어 입력을 추천 태그 조건으로 변환
- 장소명, 카테고리, 설명, 확인 메모를 기반으로 후보 태그 제안
- 블로그/후기 기반 후보 태그 정리 보조
- 추천 결과에 대한 추천 이유 문장 생성
- 관리자 검수 보조

AI가 생성한 태그는 `ai_suggested` 출처와 `candidate` 상태로 저장하며, 확인 과정을 거쳐야만 `confirmed` 상태로 전환합니다.

---

## 8. 추천 점수 반영 방향

추천 점수는 태그의 출처와 상태에 따라 다르게 반영합니다.

예시:

- `confirmed` 태그 일치: 높은 가점
- `candidate` 태그 일치: 낮은 가점
- `runtime_rule` 임시 태그 일치: 후보 판단용으로 약하게 반영
- `needs_verification` 태그: 감점 또는 안내 문구 표시
- `rejected` 태그: 추천에서 제외하거나 강한 감점

추천 점수 구성 후보:

```txt
추천 점수 =
  상황 일치 점수
+ 카테고리 일치 점수
+ 태그 일치 점수
+ 거리 점수
+ 최신 확인 점수
+ 신뢰도 점수
- 오류 제보 감점
```

초기 구현에서는 점수 계산식을 너무 복잡하게 만들기보다, 추천 결과가 설명 가능한 구조를 우선합니다.

---

## 9. 지도 API 후보와 DB 저장 장소의 차이

지도 API 결과는 추천 후보를 넓히는 용도로 사용합니다.

DB 저장 장소는 태그 출처와 검증 상태를 관리할 수 있으므로 추천 점수에서 더 높은 신뢰도를 가집니다.

추천 결과 우선순위는 다음 방향으로 둡니다.

1. 검증 태그가 있는 DB 저장 장소
2. 후보 태그가 있는 DB 저장 장소
3. 자체 수집 데이터 기반 장소
4. fixture로 준비된 태그 후보 장소
5. 지도 API 기반 임시 후보 장소

---

## 10. 현재 남은 결정 사항

- 카페 fixture 태그를 모두 추천 점수에 반영할지, 일부만 반영할지 결정해야 합니다.
- 관광지 블로그 기반 후보 태그를 fixture로 변환할지, JSON 후보 데이터로만 둘지 결정해야 합니다.
- 후보 태그를 사용자 화면에 어느 정도 노출할지 결정해야 합니다.
- 추천 카드에서 태그 출처와 신뢰도를 얼마나 자세히 표시할지 결정해야 합니다.
