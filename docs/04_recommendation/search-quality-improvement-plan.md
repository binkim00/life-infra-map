# 검색 품질 추가 개선 방안

## 목적

최종 목표는 짧은 단어, 긴 문장, 애매한 표현, 복합 조건, 부정 조건까지 자연스럽게 해석하고 문맥에 맞는 장소 추천 결과를 안정적으로 반환하는 것이다.

현재의 50개 하드 케이스 안정화 결과는 검색 품질의 기준선으로 사용한다. 이 작업은 AI 모델을 직접 학습시킨 것이 아니라, 의도 해석, 후보 수집, 필터링, 재정렬, 평가 로직을 서비스 코드에서 안정화한 결과다.

## 현재 기준선

- 안정화 문장: `docs/01_progress/search_quality_logs/search_quality_stable_50_sentences.txt`
- 반복 평가 요약: `docs/01_progress/search_quality_logs/search_quality_hard_50_r3_summary.json`
- 현재 기준: 50개 하드 케이스를 3회 반복하여 총 150회 성공
- 성공 판단 기준: 결과 존재 여부만 보지 않고, 요청 목적과 장소가 문맥적으로 맞는지 함께 확인
- 애매한 문장은 무리하게 검색하지 않고 되묻기 흐름까지 성공 기준에 포함

## 개선 원칙

1. 특정 상호명이나 특정 테스트 문장만 맞추는 하드코딩은 피한다.
2. 검색어 생성, 카테고리 매칭, 제외 조건, 후보 필터링은 일반 규칙으로 확장한다.
3. 결과 개수보다 문맥 적합성을 우선한다.
4. 애매한 요청은 바로 검색하기보다 실행 가능한 선택지로 되묻는다.
5. 되묻기 선택 후에도 이전 문맥과 위치 조건이 유지되어야 한다.
6. 웹 후보는 명시 요청이 있거나 근거 보강이 필요한 경우에만 제한적으로 사용한다.
7. 테스트는 한 번 성공으로 끝내지 않고 반복 실행과 문장 변형으로 회귀를 확인한다.

## 주요 개선 과제

### 1. 평가셋 확장

현재 50개 하드 케이스를 기준으로 삼고, 이후 100개, 150개, 200개까지 단계적으로 확장한다.

포함해야 할 유형은 다음과 같다.

- 복합 조건: `서면 근처 조용하고 콘센트 있는 카페`
- 부정 조건: `주차장 말고 바로 들어갈 수 있는 화장실`
- 목적 기반 표현: `목마른데 잠깐 뭐 마실 곳`
- 애매한 표현: `좋은 곳 추천해줘`, `놀만한 데`
- 되묻기 필요 표현: `데이트할 곳`, `실내에서 할 거`
- 잘못된 표현 또는 오타: `커피마실때`, `실내채험`
- 지역 혼합: `사상`, `서면`, `하단`, `서울역`, `강남`, `해운대`
- 일반 지도 검색이 약한 문장: `비 오는 날 실내에서 시간 보낼 곳`

각 케이스는 단순히 성공/실패만 남기지 않고 다음 정보를 기록한다.

- 원문
- 해석된 의도
- 생성된 검색어
- 사용된 위치 기준
- 후보 출처별 개수
- 최종 결과 상위 목록
- 문맥 적합성 판단
- 실패 원인

### 2. 카테고리 매칭 고도화

현재 문제의 핵심은 검색어에 포함된 단어만 보고 후보가 살아남는 경우다. 예를 들어 `카페`라는 단어가 상호명에 들어가도 실제 카페가 아니면 제외되어야 하고, `전시`라는 단어가 들어가도 박물관, 갤러리, 전시장 맥락이 아니면 낮게 봐야 한다.

개선 방향은 다음과 같다.

- Kakao 카테고리와 내부 목적 카테고리를 명확히 매핑
- 상호명 키워드 일치보다 업종/카테고리 일치를 우선
- `실내 체험`, `쇼핑몰`, `술집/바`, `전시`, `카페`, `쌀국수`처럼 오탐이 잦은 목적군을 별도 회귀 세트로 관리
- `센터`, `경로당`, `마음쉼터`, 사무실, 관리소처럼 일반 방문 목적과 어긋나는 장소는 목적별 제외 규칙에 반영
- 후보가 부족할 때만 검색어를 넓히고, 넓힌 검색어로 들어온 후보는 더 엄격하게 검증

### 3. 되묻기 품질 개선

되묻기는 사용자가 선택했을 때 실제 검색 품질이 좋아져야 의미가 있다. 선택지만 자연스럽고, 선택 후 결과가 약하면 되묻기 자체가 실패다.

개선 방향은 다음과 같다.

- 되묻기 옵션은 반드시 실행 가능한 검색 프레임과 연결
- `놀거리/액티비티` 선택 후 `실내 체험`, `야외 활동`, `아이와 함께`, `혼자 가능` 같은 옵션이 검색어와 필터에 정확히 반영
- 옵션 선택 후 결과 수가 급감하거나 검색어가 이상하게 좁아지는 문제 점검
- 되묻기 흐름에서도 이전 위치, 제외 조건, 목적이 유지되는지 테스트
- 첫 질문, 옵션 선택, 추가 조건 입력까지 다단계 대화 로그를 평가셋에 포함

### 4. 후보 수집 전략 개선

결과가 적은 이유가 실제로 주변에 장소가 없어서인지, 후보 수집이나 필터링이 너무 강해서인지 구분해야 한다.

개선 방향은 다음과 같다.

- DB, Kakao, 웹 후보 수를 단계별로 기록
- 후보가 수집되었는데 최종 결과에서 줄어든 경우 필터링 사유를 남김
- Kakao 검색어는 목적별로 여러 개 생성하되, 의미가 흐려지지 않게 제한
- 웹 검색은 기본 후보가 약하거나 사용자가 명시적으로 요구할 때만 사용
- 결과가 부족하면 재검색을 기다리게 하기보다 이미 수집한 후보를 더 보여주는 방식 우선 검토

### 5. 재정렬 및 필터링 개선

AI 재정렬은 후보를 잘 고르는 역할이어야 하고, 기본 정책 필터를 대신해서는 안 된다.

개선 방향은 다음과 같다.

- AI 재정렬 전 1차 정책 필터 적용
- AI 재정렬 후에도 부정 조건, 업종 불일치, 지역 불일치 재검증
- 재정렬 일부 실패 시 상위 결과가 너무 적게 남지 않도록 보강 로직 유지
- 추천 이유에는 내부 점수, 내부 필드명, 영어 설명이 노출되지 않도록 방어
- 결과가 있더라도 문맥에 어긋나면 성공으로 보지 않음

### 6. 제보 데이터와 정제 데이터 활용

사용자 제보와 정제 데이터가 검색 품질을 높이는 핵심 자산이 되어야 한다.

개선 방향은 다음과 같다.

- 장소 제보 승인 후 `Place` 검색에 반영되는지 확인
- 태그 제보 승인 후 `PlaceTag` 검색과 추천 후보에 반영되는지 확인
- 승인 상태 변경 이력이 사용자 화면에서 사라지지 않게 유지
- 정제 데이터 import 재개
- 태그 신뢰도와 출처를 저장해 추천 이유와 필터링에 활용
- 테스트용 또는 잘못된 장소 데이터는 검색 후보에서 제외

### 7. 실패 UX 개선

검색 실패 시에도 사용자가 상황을 이해하고 다음 행동을 할 수 있어야 한다.

개선 방향은 다음과 같다.

- 결과 생성 실패 시 지도와 결과 목록을 성공처럼 보여주지 않음
- 실패 이유를 짧게 안내
- 재시도 버튼 제공
- 현재 지도 기준 재검색 제공
- 조건이 너무 좁은 경우 완화 가능한 조건을 제안
- 애매한 경우 바로 실패 처리하지 않고 되묻기 제공

### 8. 성능 개선

품질을 유지하면서 응답 시간을 줄여야 한다.

개선 방향은 다음과 같다.

- 동일 query, 좌표, frame 조합 캐시
- DB, Kakao, 웹 후보 수집 병렬화
- AI 재정렬 입력 후보 수를 pre-rank로 축소
- 웹 검색은 명시 요청 또는 저신뢰 상황에만 실행
- 되묻기 선택 후에는 이전 후보와 해석 결과를 재사용

## 반복 운영 절차

1. 20~50개의 새 하드 케이스를 추가한다.
2. 각 문장을 지역, 표현, 조건을 조금씩 바꿔 3회 이상 반복 실행한다.
3. 결과 존재 여부가 아니라 상위 결과의 문맥 적합성을 확인한다.
4. 실패 원인을 `해석 실패`, `후보 부족`, `카테고리 오탐`, `필터 과함`, `되묻기 실패`, `UI 실패`로 분류한다.
5. 특정 문장용 수정이 아니라 일반 규칙 또는 데이터 품질 개선으로 해결한다.
6. 실패 묶음만 재실행한 뒤 전체 50개 기준선을 다시 돌린다.
7. 안정화된 문장 목록과 요약 로그만 남기고 상세 임시 로그는 정리한다.

## 우선순위

### P0

- 현재 50개 기준선 회귀 테스트 유지
- 지도 기준 검색, 현재 지도에서 재검색, 반경 고정 해제 안정화
- 장소 및 태그 제보 승인 후 검색 반영 확인
- 실패 시 지도와 결과가 성공처럼 보이는 문제 방지

### P1

- 쇼핑, 실내 체험, 놀거리, 전시, 술집/바 카테고리 오탐 개선
- 되묻기 선택 후 검색어와 결과 수가 달라지는 문제 개선
- 부정 조건과 제외 조건 회귀 테스트 확대
- 결과 부족 시 후보 수집 단계별 원인 로그 강화

### P2

- 정제 데이터 import 재개
- 평가셋 100개 이상 확장
- 사용자 검색 로그 기반 약점 분석
- 향후 모델 학습 또는 프롬프트 개선용 라벨 데이터셋 구축

## 장기 개선 방향

서비스 로직 안정화 이후에는 누적된 평가 로그를 학습 데이터처럼 활용할 수 있다. 다만 이 경우에도 모델만 믿는 방식이 아니라, 검색 후보 수집, 카테고리 매칭, 제외 조건, 위치 처리, UI 실패 방어는 서비스 레벨에서 계속 유지해야 한다.

장기적으로는 다음 데이터를 축적한다.

- 사용자의 원문 검색어
- AI가 해석한 목적과 조건
- 실제 검색어와 후보 출처
- 최종 노출 결과
- 사용자가 클릭하거나 선택한 장소
- 사람이 판단한 성공/실패 라벨

이 데이터가 충분히 쌓이면 프롬프트 개선, few-shot 예시 보강, 검색 평가셋 확장, 필요 시 모델 fine-tuning까지 검토할 수 있다.
