# 추천 시나리오 정의

## 1. 문서 목적

본 문서는 상황 기반 생활 장소 추천 지도 서비스에서 우선 검토할 추천 시나리오를 정리한다.

본 서비스는 단순히 장소 카테고리를 조회하는 것이 아니라, 사용자의 현재 상황과 목적을 추천 조건으로 변환하여 적합한 장소를 추천하는 것을 목표로 한다.

---

## 2. 서비스 차별화 방향

- 사용자가 카테고리를 직접 고르지 않아도 상황에 맞는 장소를 추천한다.
- 장소의 거리, 카테고리, 태그, 데이터 신뢰도를 조합해 추천 점수를 계산한다.
- 공중화장실, 공공와이파이, 공원 같은 기본 생활 인프라는 단순 조회가 아니라 추천 근거 또는 보조 정보로 활용한다.
- 확정하기 어려운 정보는 `후보 태그`로 관리하고, 추천 이유에서도 단정하지 않는다.
- 카카오 검색 결과는 기본 장소 후보로 활용하되, DB에 저장된 태그/추천 정보가 있는 경우에만 추천 점수와 추천 이유를 표시한다.
- 카카오 검색 결과는 별도 저장 없이 화면 표시용으로 사용한다.
- AI는 실제 장소명, 주소, 좌표, 운영 여부, 시설 보유 여부를 생성하지 않는다.

---

## 2.1 현재 구현된 통합 검색 흐름

현재 지도 탭은 일반 지도 검색과 AI 추천 검색을 통합해서 처리한다.

### 화면 구조

- 추천 테스트 탭은 제거되었고, 지도 탭에서 통합 검색을 수행한다.
- 일반 검색, 추천 검색, 지역 검색, 현재 지도 화면 재검색을 같은 지도/목록/상세 패널에서 표시한다.
- 빠른 상황 버튼을 통해 `조용히 작업할 곳`, `잠깐 쉴 곳`, `산책/힐링`, `흡연 가능한 곳` 검색을 실행할 수 있다.
- 검색 중에는 지도 오버레이, 목록 스켈레톤, 단계별 로딩 문구를 표시한다.

### SearchPlan

프론트엔드 SearchPlan helper는 현재 다음 값을 만든다.

- `originalQuery`
- `normalizedQuery`
- `correctionApplied`
- `searchMode`
- `targetQuery`
- `targetType`
- `categoryHint`
- `recommendationIntent`
- `preferredTags`
- `negativeTags`
- `kakaoKeywordCandidates`
- `confidence`
- `fallbackReason`

지원하는 검색 모드는 다음과 같다.

- `current_context`
- `around_location`
- `region_search`
- `simple_keyword`
- `recommendation_query`

SearchPlan의 장기 정책은 `docs/04_recommendation/search-plan-policy.md`에서 관리한다.

### 카카오 검색 + DB 보강

- 카카오 검색 결과를 기본 장소 후보로 사용한다.
- 카카오 place id와 DB `Place.external_id`가 같으면 DB 태그/추천 정보를 붙인다.
- 카카오 결과는 저장하지 않고 화면 표시용으로만 사용한다.
- 결과는 `카카오+DB`, `DB추천`, `카카오`로 구분한다.

### 병합 기준

같은 장소는 중복 표시하지 않는다.

1. `external_id === kakaoPlaceId`
2. 정규화한 장소명 유사 + 좌표 30m 이내
3. 정규화한 장소명 유사 + 주소 일부 일치

### 추천 정보 표시

- `DB추천`, `카카오+DB`는 추천 점수, 추천 이유, 추천 신뢰도, 매칭 태그를 표시한다.
- `카카오`만 있는 결과에는 추천 점수와 추천 이유를 억지로 만들지 않는다.
- 조건 만족 여부를 확인할 수 없는 경우에는 만족한다고 단정하지 않는다.

## 3. MVP 우선 구현 시나리오

## 3.1 약속 전 시간 때우기 좋은 장소 추천

### 사용자 상황

약속 시간까지 남은 시간을 보낼 수 있는 가까운 장소가 필요하다.

### 추천 대상

- 카페
- 공원
- 쉼터
- 공공시설
- 무료 와이파이 주변 장소

### 주요 태그

`잠깐쉬기`, `대기하기좋음후보`, `실내`, `야외`, `무료`, `와이파이`, `화장실`

### 초기 구현 방식

현재 위치와 가까운 장소를 우선 추천하고, 사용자가 입력한 예상 대기 시간에 따라 거리 점수와 체류 가능성 태그를 반영한다.

---

## 3.2 조용히 작업할 카페 추천

### 사용자 상황

노트북 작업이나 공부를 하기 위해 조용하고 머물기 좋은 카페를 찾고 있다.

### 추천 대상

- 카페
- 도서관 주변 카페
- 공공 와이파이 주변 카페 후보

### 주요 태그

`작업가능후보`, `와이파이`, `콘센트후보`, `조용함후보`, `혼자이용후보`

### 초기 구현 방식

카페 후보 데이터에 직접 확인 태그 또는 관리자 입력 태그를 일부 부여하고, 태그 일치도와 거리 점수를 기준으로 추천한다.

---

## 3.3 근처 산책/힐링 장소 추천

### 사용자 상황

가볍게 산책하거나 머리를 식힐 수 있는 장소가 필요하다.

### 추천 대상

- 도시공원
- 하천변
- 쉼터
- 관광지
- 명소 후보

### 주요 태그

`산책`, `휴식`, `야외`, `자연친화`, `힐링`, `경관후보`

### 초기 구현 방식

도시공원, 쉼터, 관광지 데이터를 기반으로 산책과 휴식 태그를 부여하고, 거리와 편익시설 정보를 추천 점수에 반영한다.

---

## 3.4 흡연 가능한 장소 추천

### 사용자 상황

현재 위치 근처에서 흡연 가능한 장소가 필요하다.

### 추천 대상

- 흡연구역
- 흡연실
- 실외 흡연 가능 장소 후보

### 주요 태그

`흡연`, `흡연구역`, `실외`, `실내`, `개방형`, `폐쇄형`, `관리됨`

### 초기 구현 방식

좌표가 있는 흡연구역 데이터를 우선 사용하고, 거리 점수와 데이터 출처 신뢰도를 기준으로 추천한다.

## 4. 고도화 후보 시나리오

## 4.1 드라이브 목적지 후보 추천

### 사용자 상황

가볍게 다녀올 수 있는 드라이브 목적지가 필요하다.

### 추천 대상

- 관광지
- 전망대
- 공원
- 호수
- 해안
- 하천변

### 주요 태그

`드라이브후보`, `경관후보`, `야외`, `휴식`, `주차가능`

### 보류 이유

실제 드라이브 적합성, 도로 경관, 주차 난이도를 판단할 데이터가 부족하므로 고도화 기능으로 둔다.

---

## 4.2 야경 보기 좋은 장소 후보 추천

### 사용자 상황

밤에 가볍게 방문할 수 있는 야경 감상 장소가 필요하다.

### 추천 대상

- 전망대
- 공원
- 하천변
- 관광지
- 명소 후보

### 주요 태그

`야경후보`, `경관후보`, `야외`, `산책`, `드라이브후보`

### 보류 이유

야경 품질, 야간 개방 여부, 야간 안전성을 확정하기 어려우므로 `야경후보`로만 관리한다.

---

## 4.3 비 오는 날 갈 만한 장소 추천

### 사용자 상황

비가 오는 날에도 이용하기 좋은 실내 장소가 필요하다.

### 추천 대상

- 카페
- 도서관
- 공공시설
- 문화시설
- 실내 쉼터

### 주요 태그

`실내`, `작업가능후보`, `휴식`, `공공시설`, `카페`

### 보류 이유

날씨 연동과 실내 장소 데이터 보강이 필요하므로 고도화 기능으로 둔다.

---

## 4.4 혼자 있기 좋은 장소 추천

### 사용자 상황

혼자 조용히 시간을 보내거나 부담 없이 머물 장소가 필요하다.

### 추천 대상

- 카페
- 공원
- 도서관
- 쉼터
- 산책 장소

### 주요 태그

`혼자이용후보`, `조용함후보`, `휴식`, `산책`, `작업가능후보`

### 보류 이유

분위기, 혼잡도, 좌석 구조를 확인하기 어려우므로 초기에는 후보 태그로만 관리한다.

---

## 4.5 이동 중 급한 상황 해결 장소 추천

### 사용자 상황

이동 중 급하게 화장실, 흡연구역, 주차장 등 생활 편의 장소가 필요하다.

### 추천 대상

- 공중화장실
- 흡연구역
- 주차장
- 공공시설

### 주요 태그

`급할때`, `생활불편해결`, `화장실`, `흡연`, `주차가능`, `24시간`

### 보류 이유

단순 생활 인프라 조회처럼 보일 수 있으므로, MVP 핵심보다는 보조 시나리오로 활용한다.

## 5. MVP 우선순위

| 우선순위 | 시나리오 | 판단 |
|---|---|---|
| 1 | 약속 전 시간 때우기 좋은 장소 추천 | 상황 기반 추천 차별성이 큼 |
| 2 | 조용히 작업할 카페 추천 | 사용자 니즈가 명확함 |
| 3 | 근처 산책/힐링 장소 추천 | 공공데이터와 추천 로직을 함께 활용 가능 |
| 4 | 흡연 가능한 장소 추천 | 생활 불편 해결형으로 차별성이 있음 |

## 6. 초기 구현 제외 기준

초기 구현에서는 아래 내용을 확정 정보로 제공하지 않는다.

- 조용한 카페 확정
- 콘센트 있음 확정
- 노트북 작업 가능 확정
- 야경 명소 확정
- 드라이브 코스 확정
- 실시간 주차 가능 여부
- 실시간 혼잡도
- 현재 운영 여부

위 정보들은 데이터로 직접 확인되지 않는 경우 `후보 태그` 또는 고도화 기능으로 관리한다.

## 7. 현재 구현된 검색 품질 보정

### 7.1 오타 보정

현재 검색 전 일부 오타와 축약어를 보정한다.

| 입력 | 보정 |
|---|---|
| 카패 | 카페 |
| 와파이 | 와이파이 |
| 콘샌트 | 콘센트 |
| 놋북 | 노트북 |
| 흡구 | 흡연구역 |
| 공화 | 공중화장실 |
| 공와 | 공공와이파이 |
| 작엄 | 작업 |

지역명과 장소명은 무리하게 보정하지 않는다.

### 7.2 추상 표현 처리

`곳`, `장소`, `데`, `갈만한 곳`, `쉴 곳`, `작업할 곳` 같은 표현은 실제 장소명이 아니라 추상 표현으로 본다.

현재 구현은 `targetType=abstract`로 분류하고, 추천 의도에 맞는 카카오 검색 후보 키워드를 생성한다.

예:

```text
근처 작업가능한 곳
→ work_cafe 의도
→ 카페, 작업 카페, 공부 카페, 스터디카페 후보 검색
```

### 7.3 대표 장소/부속 시설 정렬

사용자가 주차장/화장실을 직접 찾는 경우가 아니라면 아래 부속 시설을 대표 장소보다 후순위로 정렬한다.

- 주차장
- 공중화장실
- 화장실
- 관리사무소
- 매표소
- 안내소
- 입구
- 출입구
- 정문
- 후문
- 승강장
- 정류장

공원, 관광명소, 문화시설, 해수욕장, 전망대, 산책로 등은 대표 장소 후보로 가산한다.

1차 카카오 결과가 부속 시설뿐이면 대표 장소명을 추출해 보조 검색을 1회 수행한다.

### 7.4 waiting_place 부적합 쉼터 필터링

`잠깐 쉴 곳`, `비 오는데 잠깐 쉴 곳`, `더운데 쉴 곳` 같은 waiting_place 검색에서는 일반 이용 가능성이 높은 실내 대기/휴식 장소를 우선한다.

강한 제외/후순위 대상:

- 경로당
- 노인정
- 노인회관
- 마을회관
- 사랑방
- 사랑터
- 복지관
- 노인복지
- 요양원
- 어린이집
- 유치원
- 학교

강한 감점 대상:

- 행정복지센터
- 주민센터
- 동사무소
- 구청
- 시청
- 민원센터

부적합 후보에는 “잠깐 쉬기 좋은 후보입니다” 같은 긍정 추천 이유를 붙이지 않는다.

## 8. 카카오 상세/길찾기

- DB추천 장소라도 `source=kakao_local`이고 `external_id`가 있으면 카카오 상세 URL을 만든다.
- 카카오 상세 URL이 있으면 DB 요약 카드보다 카카오 상세 iframe 또는 링크를 우선한다.
- 좌표가 있는 모든 장소에 “카카오맵 길찾기” 버튼을 표시한다.
- 현재 위치 좌표가 있으면 출발지와 도착지를 포함한 길찾기 URL을 만든다.
- 현재 위치 권한이 없거나 좌표가 없으면 도착지만 지정하는 길찾기 URL로 fallback한다.

## 9. 실시간 검색 결과 태그 부여 방식

본 서비스는 모든 장소 데이터를 자체 DB에 저장하지 않는다.

카페, 관광지, 드라이브 목적지 후보, 야경 후보처럼 자체 데이터 확보가 어려운 장소는 지도 API의 실시간 장소 검색 결과를 활용할 수 있다.

지도 API 검색 결과에는 추천 시점에 임시 태그를 부여한다.

임시 태그는 추천 점수 계산과 결과 표시에는 활용하지만, 별도 검증이나 사용자 저장이 없는 경우 DB에 영구 저장하지 않는다.

자체 DB에는 공공데이터 기반 장소, 팀이 직접 확인한 장소, 관리자 검증 장소, 사용자 저장 또는 검증을 통해 관리가 필요한 장소만 저장한다.

| 구분 | 저장 위치 | 설명 |
|---|---|---|
| verified_tags | DB PlaceTag | 검증된 장소 태그 |
| runtime_tags | API 응답 메모리 | 지도 API 검색 결과에 임시 부여하는 태그 |
| scenario_scores | 추천 계산 결과 | 거리, 상황 적합도 등 요청마다 달라지는 점수 |

## 10. 남은 개선 사항

### 10.1 조건 충돌 검색 처리

아래 검색은 아직 공통 정책 구현이 더 필요하다.

- 흡연 가능한 맥도날드
- 콘센트 있는 맥도날드
- 주차 가능한 해수욕장
- 조용한 술집

개선 방향:

- target을 버리지 않는다.
- 조건은 target에 붙는 조건으로 분리한다.
- 조건 만족 여부를 확인할 수 없으면 “확인되지 않음”으로 안내한다.
- fallbackTarget은 별도 그룹으로 표시한다.

### 10.2 식당/음식 검색 처리

아래 검색은 현재 카카오 일반 검색 수준으로는 처리 가능하지만, 추천 정책은 더 필요하다.

- 근처 맛집
- 근처 식당
- 혼밥하기 좋은 식당
- 소금빵 맛집

개선 방향:

- 음식/상품 키워드를 위치로 오인하지 않는다.
- 식당/음식/브랜드를 target으로 분리한다.
- 혼밥, 조용함, 주차 가능 등은 condition으로 분리한다.

### 10.3 SearchPlan 백엔드화

현재 SearchPlan은 프론트 helper 중심이다.

향후 개선:

- 백엔드 SearchPlan API 추가
- AI가 `location`, `target`, `conditions`, `fallbackTargets`, `resultPolicy` 구조를 JSON으로 반환
- 사용자 입력과 Tag/Category 설명 간 임베딩 기반 의미 매칭 검토
