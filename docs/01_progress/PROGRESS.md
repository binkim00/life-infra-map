## 3일차

### 진행 요약

- 프로젝트 방향을 “상황 기반 생활 장소 추천 지도 서비스”로 재정리했습니다.
- 서비스의 중심을 단순 지도 조회가 아니라 사용자의 위치와 상황에 맞는 장소 추천으로 조정했습니다.
- 생활 불편 해결형 장소와 상황/목적 기반 추천 장소를 구분했습니다.
- 사용자 제보, 후기, 검증은 초기 데이터 수집의 해결책이 아니라 서비스 운영 중 정보 보완 기능으로 분리하기로 했습니다.
- 카페, 산책, 드라이브, 힐링 장소처럼 공공데이터만으로 확보하기 어려운 데이터의 수집 방안을 검토했습니다.
- 지도 API에서 이미 검색 가능한 기본 장소 정보는 대량 저장하기보다 실시간 검색 후보로 활용하는 방향을 논의했습니다.
- 네이버 플레이스 방문자 리뷰 키워드 기반 태그화 가능성을 테스트했습니다.
- 부산 전포 카페를 대상으로 방문자 리뷰 상단 대표 키워드 일부가 추출되는 것을 확인했습니다.
- 다만 대표 키워드만으로는 조용함, 콘센트 있음, 와이파이 있음, 노트북 작업 가능 등 핵심 태그를 충분히 확보하기 어렵다는 한계를 확인했습니다.
- 태그는 고정 정보로 저장하기보다 출처, 신뢰도, 확인일, 상태값을 함께 관리해야 한다는 점을 정리했습니다.

## 4일차

### 진행 요약

- 프로젝트 문서 구조를 정리하고, DB 설계서, ERD, 데이터 정제 기준, 태그 자동 부여 규칙, 추천 시나리오 문서를 작성했습니다.
- 기존 방향을 “장소 데이터를 모두 DB에 저장하는 구조”가 아니라, 지도 API 실시간 검색 결과와 자체 데이터를 함께 활용하는 혼합형 추천 구조로 재정리했습니다.
- 추천 시나리오는 약속 전 시간 때우기, 조용히 작업할 카페, 산책/힐링 장소, 흡연구역 추천을 MVP 후보로 정리했습니다.
- 태그는 모든 장소에 저장하지 않고, 저장 태그, 임시 태그, 계산 값으로 구분하기로 했습니다.
- 지도 API로 검색된 장소에는 추천 시점에 임시 태그를 부여하고, 검증된 장소나 자체 수집 데이터에만 저장 태그를 관리하는 방향으로 정리했습니다.
- Django 백엔드와 Vue 프론트엔드 프로젝트를 생성했습니다.
- Django REST Framework와 CORS 설정을 완료했습니다.
- 추천 목업 API를 생성하고, Vue에서 axios로 API 응답을 받아 추천 카드 형태로 출력하는 테스트를 진행했습니다.
- 카카오 REST API 키를 연결하고, 카카오 로컬 API를 통해 주변 장소 검색이 가능한지 테스트했습니다.
- 카카오 로컬 API 검색 결과를 우리 서비스의 추천 응답 구조로 변환했습니다.
- 카카오 JavaScript SDK를 연결하여 프론트 화면에 지도를 표시했습니다.
- 브라우저 현재 위치를 가져와 백엔드 추천 API에 위도와 경도를 전달하는 흐름을 테스트했습니다.
- 추천 결과의 위도와 경도를 기반으로 지도에 마커를 표시하고, 마커 클릭 시 간단한 정보창이 표시되는 것을 확인했습니다.
- 카페와 산책/힐링 시나리오는 카카오 API 실시간 검색 기반으로 추천 가능함을 확인했습니다.
- 흡연구역은 카카오 API 검색 결과가 부족하여 자체 수집 JSON 데이터를 활용하는 방식으로 분리했습니다.
- 자체 흡연구역 JSON 데이터를 읽어 현재 위치 기준 거리를 계산하고, 가까운 흡연구역을 추천 결과로 반환하는 테스트에 성공했습니다.
- 카카오 API 검색 결과와 자체 수집 데이터를 동일한 추천 응답 구조로 변환하여 추천 카드와 지도 마커에 함께 사용할 수 있음을 확인했습니다.

### 다음 작업

- 지도 API 테스트 결과를 `map-api-test.md`에 정리
- 흡연구역 자체 데이터 처리 코드 정리

- 자체 데이터와 지도 API 결과를 함께 사용하는 구조 문서화

## 5일차

### 진행 요약

- 지도 API 검색 결과를 단순히 추천 목록과 지도 마커로 표시하는 것만으로는 기존 지도 서비스와 차별성이 부족하다고 판단했습니다.
- 프로젝트의 핵심을 지도 API 검색이 아니라 추천 가치 태그 기반 장소 추천 구조로 재정리했습니다.
- 지도 API는 장소 후보 수집과 지도 표시를 위한 보조 수단으로 사용하고, 서비스의 핵심은 태그의 출처, 상태, 검증 여부, 신뢰도 관리에 두기로 했습니다.
- 태그를 카테고리/필터용 태그와 추천 가치 태그로 구분하기로 했습니다.
- 모든 지도 API 결과를 DB에 저장하지 않고, 자체 수집 데이터, 팀 확인 장소, 사용자 저장/검증 장소만 DB 관리 대상으로 두기로 했습니다.
- DB에 저장된 장소는 Place, Tag, PlaceTag 구조로 관리하고, PlaceTag에 태그 출처, 상태, 신뢰도, 검증 여부, 근거 정보를 함께 저장하는 방향으로 정리했습니다.
- AI는 실제 장소 정보를 임의 생성하거나 태그를 확정하는 용도가 아니라, 자연어 입력을 추천 태그 조건으로 변환하고 후보 태그와 추천 이유를 생성하는 보조 역할로 활용하기로 했습니다.

### 다음 작업

- 추천 가치 태그 사전 작성
- 태그 확보 전략 문서 작성

- 기존 기획과 팀원 제안의 차이를 비교했습니다.
- 기존 기획은 실제 확보 가능한 장소 데이터 기반 추천에 초점이 있고, 팀원 제안은 자연어 검색과 후기 기반 추가 태그 후보 생성에 초점이 있음을 확인했습니다.

- 통합 방향을 `docs/00_project/service-direction.md` 문서로 추가했습니다.
- `docs/00_project/ROADMAP.md`를 통합 방향에 맞게 보강했습니다.
