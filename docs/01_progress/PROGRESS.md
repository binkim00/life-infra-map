## 3일차

### 진행 요약

- 프로젝트 방향을 “상황 기반 생활 장소 추천 지도 서비스”로 재정리했습니다.
- 서비스의 중심을 단순 지도 조회가 아니라 사용자의 위치와 상황에 맞는 장소 추천으로 조정했습니다.
- 생활 불편 해결형 장소와 상황/목적 기반 추천 장소를 구분했습니다.
- 사용자 제보, 후기, 검증은 초기 데이터 수집의 해결책이 아니라 서비스 운영 중 정보 보완 기능으로 분리하기로 했습니다.
- 카페, 산책, 드라이브, 힐링 장소처럼 공공데이터만으로 확보하기 어려운 데이터의 수집 방안을 검토했습니다.
- 지도 API에서 이미 검색 가능한 기본 장소 정보는 대량 저장하기보다 실시간 검색 후보로 활용하는 방향을 논의했습니다.
- 네이버 플레이스 방문자 리뷰 키워드 기반 태그화 가능성을 테스트했습니다.
- 부산 전포 카페를 대상으로 방문자 리뷰 상단 대표 키워드 일부가 추출되는 것을 확인했습니다.
- 다만 대표 키워드만으로는 조용함, 콘센트 있음, 와이파이 있음, 노트북 작업 가능 등 핵심 태그를 충분히 확보하기 어렵다는 한계를 확인했습니다.
- 태그는 고정 정보로 저장하기보다 출처, 신뢰도, 확인일, 상태값을 함께 관리해야 한다는 점을 정리했습니다.

## 4일차

### 진행 요약

- 프로젝트 문서 구조를 정리하고, DB 설계서, ERD, 데이터 정제 기준, 태그 자동 부여 규칙, 추천 시나리오 문서를 작성했습니다.
- 기존 방향을 “장소 데이터를 모두 DB에 저장하는 구조”가 아니라, 지도 API 실시간 검색 결과와 자체 데이터를 함께 활용하는 혼합형 추천 구조로 재정리했습니다.
- 추천 시나리오는 약속 전 시간 때우기, 조용히 작업할 카페, 산책/힐링 장소, 흡연구역 추천을 MVP 후보로 정리했습니다.
- 태그는 모든 장소에 저장하지 않고, 저장 태그, 임시 태그, 계산 값으로 구분하기로 했습니다.
- 지도 API로 검색된 장소에는 추천 시점에 임시 태그를 부여하고, 검증된 장소나 자체 수집 데이터에만 저장 태그를 관리하는 방향으로 정리했습니다.
- Django 백엔드와 Vue 프론트엔드 프로젝트를 생성했습니다.
- Django REST Framework와 CORS 설정을 완료했습니다.
- 추천 목업 API를 생성하고, Vue에서 axios로 API 응답을 받아 추천 카드 형태로 출력하는 테스트를 진행했습니다.
- 카카오 REST API 키를 연결하고, 카카오 로컬 API를 통해 주변 장소 검색이 가능한지 테스트했습니다.
- 카카오 로컬 API 검색 결과를 우리 서비스의 추천 응답 구조로 변환했습니다.
- 카카오 JavaScript SDK를 연결하여 프론트 화면에 지도를 표시했습니다.
- 브라우저 현재 위치를 가져와 백엔드 추천 API에 위도와 경도를 전달하는 흐름을 테스트했습니다.
- 추천 결과의 위도와 경도를 기반으로 지도에 마커를 표시하고, 마커 클릭 시 간단한 정보창이 표시되는 것을 확인했습니다.
- 카페와 산책/힐링 시나리오는 카카오 API 실시간 검색 기반으로 추천 가능함을 확인했습니다.
- 흡연구역은 카카오 API 검색 결과가 부족하여 자체 수집 JSON 데이터를 활용하는 방식으로 분리했습니다.
- 자체 흡연구역 JSON 데이터를 읽어 현재 위치 기준 거리를 계산하고, 가까운 흡연구역을 추천 결과로 반환하는 테스트에 성공했습니다.
- 카카오 API 검색 결과와 자체 수집 데이터를 동일한 추천 응답 구조로 변환하여 추천 카드와 지도 마커에 함께 사용할 수 있음을 확인했습니다.

### 다음 작업

- 지도 API 테스트 결과를 `map-api-test.md`에 정리
- 흡연구역 자체 데이터 처리 코드 정리

- 자체 데이터와 지도 API 결과를 함께 사용하는 구조 문서화

## 5일차

### 진행 요약

- 지도 API 검색 결과를 단순히 추천 목록과 지도 마커로 표시하는 것만으로는 기존 지도 서비스와 차별성이 부족하다고 판단했습니다.
- 프로젝트의 핵심을 지도 API 검색이 아니라 추천 가치 태그 기반 장소 추천 구조로 재정리했습니다.
- 지도 API는 장소 후보 수집과 지도 표시를 위한 보조 수단으로 사용하고, 서비스의 핵심은 태그의 출처, 상태, 검증 여부, 신뢰도 관리에 두기로 했습니다.
- 태그를 카테고리/필터용 태그와 추천 가치 태그로 구분하기로 했습니다.
- 모든 지도 API 결과를 DB에 저장하지 않고, 자체 수집 데이터, 팀 확인 장소, 사용자 저장/검증 장소만 DB 관리 대상으로 두기로 했습니다.
- DB에 저장된 장소는 Place, Tag, PlaceTag 구조로 관리하고, PlaceTag에 태그 출처, 상태, 신뢰도, 검증 여부, 근거 정보를 함께 저장하는 방향으로 정리했습니다.
- AI는 실제 장소 정보를 임의 생성하거나 태그를 확정하는 용도가 아니라, 자연어 입력을 추천 태그 조건으로 변환하고 후보 태그와 추천 이유를 생성하는 보조 역할로 활용하기로 했습니다.

### 다음 작업

- 추천 가치 태그 사전 작성
- 태그 확보 전략 문서 작성

- 기존 기획과 팀원 제안의 차이를 비교했습니다.
- 기존 기획은 실제 확보 가능한 장소 데이터 기반 추천에 초점이 있고, 팀원 제안은 자연어 검색과 후기 기반 추가 태그 후보 생성에 초점이 있음을 확인했습니다.

- 통합 방향을 `docs/00_project/service-direction.md` 문서로 추가했습니다.
- `docs/00_project/ROADMAP.md`를 통합 방향에 맞게 보강했습니다.

후보 수집(DB 30건 + 카카오 15건)까지는 정상이었고, AI 후보 평가(reranker) 단계에서 결과가 전량 폐기되고 있었습니다.

원인은 네 가지였습니다.

* `AI_RERANK_TIMEOUT`이 7초였는데 실제 호출은 12~14초가 걸려 항상 `ReadTimeout`이 났습니다.
  * 응답 시간의 대부분은 reasoning 토큰이었습니다. (1408~1472 토큰)
  * openai 경로만 reasoning effort를 지정하지 않고 있었습니다. gms 경로는 이미 `minimal`로 보내고 있었습니다.
* reranker 프롬프트에 "후보마다 한 행씩 반환하라"는 지시가 없고 예시 배열 원소가 1개뿐이라, 후보 8~15건을 보내도 **1건만** 응답했습니다.
  * 나머지는 `missing_candidate_decision`으로 분류되어 화면에서 사라졌습니다.
* 프롬프트에 `semantic_score` 기준이 없어 모델이 전부 0을 반환했습니다.
  * `urgent_nearest` 정책은 `semantic_score >= 40`으로 거르기 때문에, 평가에 성공해도 급한 상황 질의는 0건이 됐습니다.
* reranker가 실패하면 대체 정렬 없이 결과를 통째로 버리고 오류 문구만 표시했습니다.

수정 내용입니다.

* reranker 호출에 reasoning effort를 지정할 수 있게 `call_ai_json`에 `reasoning_effort` 인자를 추가했습니다.
  * `AI_RERANK_REASONING_EFFORT` 기본값 `low`. 호출 12.3초 -> 1.7~6초로 줄었습니다.
* `AI_RERANK_TIMEOUT` 기본값을 7초에서 20초로 올리고 상한을 40초로 넓혔습니다.
* `AI_SEARCH_RERANK_MAX_CANDIDATES` 기본값을 15에서 8로 낮춰 한 번의 호출 부담을 줄였습니다.
* 프롬프트에 후보 수만큼 행을 반환하도록 명시하고, 입력에 `candidate_count`를 함께 보냅니다.
* 프롬프트에 `semantic_score` 구간 기준을 명시했습니다. (include 70~100, needs_verification 40~69, exclude 0~39)
* reranker가 실패해도 수집한 후보를 사전 근거/거리 순서로 표시하는 fallback을 넣었습니다.
  * 기존 `_top_up_ranked_candidates`를 재사용해 추천 이유를 지어내지 않습니다.
  * `debug_pipeline`에 `ranking_fallback_applied`로 남깁니다.
* 추천 이유에서 `프레임`, `타깃`, `타겟` 같은 내부 용어를 걸러내도록 했습니다.

### 검색 속도

단계별로 재보니 AI 검색 시간의 95~98%가 reranker 한 곳이었습니다.

| 단계 | 시간 |
| --- | --- |
| intent planner | 0.2~2ms (local rule, AI 호출 없음) |
| retrieval (DB + 카카오) | 222~417ms |
| reranker | 5,301~18,818ms |

reranker를 더 줄이는 방법을 실측했는데, 전부 정확도를 깎았습니다.

| 방안 | 속도 | 판정 품질 |
| --- | --- | --- |
| reasoning effort `minimal` | 3.1초 | 8건 중 2건만 판정 (`partial_executed`) |
| max_output_tokens 1200 | - | 응답 잘림 (`invalid_response`) |
| 4건씩 2배치 병렬 | 5.2~6.6초 | 이득 약 1초, 배치가 서로를 못 봐 비교 판정 저하 |
| 현행 (`low` / 2500 / 8건) | 6.3~7.6초 | `executed`, 미판정 0 |

그래서 판정 설정은 그대로 두고, 정확도에 영향이 없는 캐시를 넣었습니다.

* 같은 후보 묶음(frame + ranking_policy + 후보 목록)에 대한 AI 판정을 재사용합니다.
  * 캐시 키는 모델에 보내는 요청 본문 그대로의 sha256이라 입력이 조금이라도 다르면 새로 호출합니다.
  * 판정 내용을 그대로 쓰고 호출만 건너뛰므로 결과 목록과 순서가 동일합니다.
* `AI_RERANK_CACHE_TTL` 기본 900초. 테스트에서는 각 케이스가 실제 호출 경로를 타야 하므로 0으로 둡니다.

| 질의 | 첫 호출 | 재호출 |
| --- | --- | --- |
| 지금 화장실 급해 | 6.3초 | **0.2초** |
| 근처에 주차할 곳 | 5.6초 | **0.3초** |

### 카테고리 질의 라우팅

카테고리와 거리로 답이 정해지는 요청은 AI 후보 평가를 건너뛰도록 했습니다.

* `_deterministic_category_codes(frame)`가 라우팅 대상인지 판단합니다.
  * target/result/candidate 표현이 전부 `toilet`, `parking`, `freewifi`, `shelter`, `smoking_area`로 떨어질 때만 라우팅합니다.
  * `exclusions`가 있거나, 후보를 걸러내는 조건이 하나라도 있으면 AI 경로를 그대로 씁니다.
  * `긴급`, `가까운 곳` 같은 거리·긴급도 표현은 정렬 정책에 이미 반영돼 있어 라우팅을 막지 않습니다.
* 라우팅 시 후보 집합은 AI가 평가했을 집합(`evidence_candidates`)을 그대로 쓰고 순서만 거리순으로 정합니다.
  * 걸러내는 기준을 새로 만들지 않아 recall이 줄지 않습니다.
  * 추천 이유는 실제 거리와 카테고리명만 씁니다.
* `AI_SEARCH_ROUTE_CATEGORY_REQUESTS=false`로 끌 수 있습니다.

### 지명 앵커 오해석

사용자가 그 지역에 없으면 지명이 엉뚱하게 풀렸습니다. 센텀에서 `서면 화장실`이 **서면손칼국수**(수영구 음식점)를 기준점으로 잡아 연제구 화장실을 줬습니다.

* 상호명에 지명이 우연히 들어간 상업 시설을 기준점에서 배제했습니다.
  * 이름이 정확히 일치하지 않고 카테고리가 음식점/학원/학교/소매 등이면 감점합니다.
  * `서면손칼국수`는 걸러지고, 사용자가 `서면손칼국수`라고 정확히 입력하면 그대로 씁니다.
* `MIN_ANCHOR_RESOLUTION_SCORE` 미달 후보는 쓰지 않고 위치 확인 실패로 처리합니다.

다만 **근본 한계가 남았습니다.** 카카오 키워드 검색은 센텀 기준으로 `서면`을 검색해도 서면역·서면교차로를 반환하지 않고 상호명에 서면이 든 가게만 줍니다. 좌표 없이 검색하면 순천시 서면이 나옵니다. `서면` 같은 통칭 지명은 카카오 장소 검색으로 해결되지 않습니다.

### 지명 사전 도입

카카오 장소 검색은 통칭 지명을 지명으로 풀지 못합니다. 사용자 근처를 검색하면 상호명에 그 단어가 든 가게가 나오고, 좌표 없이 검색하면 엉뚱한 지역이 나옵니다.

`area_gazetteer.py`를 추가해 자주 쓰는 지명 41개를 카카오에 묻기 전에 먼저 해결합니다.

* 좌표는 지어낸 값이 아니라 **DB에 저장된 장소들의 주소로 묶어 중앙값**을 낸 값입니다.
  * 예: `서면` = 부전동 표본 83건의 중앙값 (35.156790, 129.056416)
  * 주석에 근거 표본 수를 남겼습니다.
* `서면역`, `광안리 근처`, `해운대 일대`처럼 뒤에 붙는 표현은 잘라내고 찾습니다.
* 카카오까지 실패하면 낱말 단위로 한 번 더 찾습니다. (`서면 맛집거리` -> `서면`)
* AI가 지명을 빠뜨리면 규칙으로 찾은 지명으로 채웁니다. (`광안리 맛집` -> anchor 없음 문제)

결과: 사용자가 서면·센텀·서울·대전·광주 어디에 있든 `서면`이 항상 부산진구 서면으로 풀립니다.

### 야경/드라이브가 되묻기로 빠지던 문제

`야경 보기 좋은 곳`, `드라이브 갈 만한 곳`이 목적이 분명한데도 clarification으로 빠져 0건이었습니다.

* `broad_place_has_specific_target` 목록에 야경/드라이브가 없어 막연한 요청으로 분류됐습니다.
* DB에 대응 태그가 있으므로(`야경` 348건, `전망좋음` 308건, `드라이브목적지` 189건) 바로 검색하도록 규칙을 추가했습니다.
* `드라이브`는 target_objects에 그대로 넣어야 `갈 만한 곳`이 막연한 요청으로 재분류되지 않습니다.
