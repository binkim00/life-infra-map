# 검색 엔진·대화 품질 개선 완료 보고

2026-10-06. 검색 엔진과 대화 상태 수정, 웹·모바일 연결 코드, 운영 Django·웹 배포 및 공개 API 검증을 완료했다. 모바일 변경은 소스·타입·린트 검증까지이며 새 APK 설치·실기기 터치 검증은 이번 작업에서 실행하지 않았다.

## 1. 공개 400 실제 원인

공개 검색 경로는 `/django/api/recommendations/place-search/`이다. 운영 Django의 실제 `ALLOWED_HOSTS`에 `yeogiljido.com`이 없었고 게이트웨이가 공개 Host를 전달해 Django가 HTML 400을 반환했다. 같은 Host를 사용하는 내부 요청에서도 재현했다. CORS·CSRF 목록에도 공개 HTTPS 주소가 없었다.

사용자 승인 후 환경 파일을 백업하고 세 목록에 공개 주소를 추가했다. Django 환경 파일과 API Compose 환경 파일을 함께 전달해 재생성했다. 최종 공개 JSON HTTP 200과 `Access-Control-Allow-Origin: https://yeogiljido.com`을 확인했다. 앞선 AWS 인증 페이지 400과 서비스 검색 API의 Host 거부는 별개 현상이다.

## 2. 부분 충족·UNKNOWN 후보가 들어오던 경로

- `_allow_sparse_expansion`, `_top_up_ranked_candidates`, `_complete_and_order_results`가 부족한 개수를 넓은 후보·부분 일치로 보충했다.
- 조건별 정책 추론을 확인된 근거처럼 사용하는 경로와 부분 문자열 일치가 있었다. 예를 들어 부정 문구가 긍정 조건을 뒷받침할 수 있었다.
- 필수조건 검증이 최종 응답과 후보 미리보기 전체에 일관되게 적용되지 않았다.

기본 보충을 차단하고 최종 결과·후보 미리보기에 같은 필수조건 검증을 적용했다. 정책 추론·추천 태그는 확인된 외부 사실로 승격하지 않는다.

## 3. 변경한 기본 추천 정책

활성화된 모든 긍정 필수조건에 명시적 긍정 근거가 있어야 기본 결과에 들어간다. 필수조건 UNKNOWN·CONFLICTED·부정 근거·위반이 있으면 제외한다. 선호조건 미확인은 필수조건으로 승격하지 않는다. 필수조건 수를 임의로 잘라 검사하지 않는다.

결과가 부족해도 개수 채우기, 자동 반경 확대, 대상 변경을 하지 않는다. 미확인 후보는 명시적인 `show_unverified` 행동에서만 허용한다. 평가 모델 실패 시에도 직접 대상/업종 근거와 모든 필수조건 근거가 있는 후보만 제한적으로 사용한다. 이해한 후속 조건에서 근거가 부족한 경우 검색 결과 0건으로 처리하며, 실제 최초 공급자 통신 오류는 정상 0건으로 위장하지 않는다.

## 4. 기존 대화 상태 문제

후속 발화를 새 검색처럼 해석하면서 지역·대상·조건이 소실되고, UI가 가진 이전 검색 상태가 서버 상태를 덮을 수 있었다. 설명·비교 후 결과 순번이 재정의될 수 있었고 clarification 및 실패가 기존 결과를 지웠다. 유효한 조건 변경 뒤 평가 실패가 발생하면 변경 이력이 누락되어 undo가 더 오래된 조건까지 되돌리는 문제도 운영 연속 검증에서 발견했다.

서버 세션을 기준으로 frame, 결과 snapshot, 참조, 선택, 제외, 의미 변경 이력을 유지한다. 유효한 조건 patch는 이후 평가 실패 여부와 관계없이 undo 이력에 기록한다.

## 5. 추가·교체·제거·필수↔선호 구현

`conversation_patches.py`에서 현재 frame의 복사본에 의미 변경을 적용한다. 구조화 조건은 `requirement`, `polarity`, `source_turn`, `active`, `type`, `value`를 유지한다.

- 추가: `주차 필수` 뒤 `콘센트도 필수`는 두 조건을 누적한다.
- 제거: `주차 조건 취소`는 주차만 비활성화하고 콘센트를 유지한다.
- 교체: `주차 대신 콘센트`는 주차를 제거하고 콘센트를 추가한다.
- 요구 수준: `콘센트는 있으면 좋아`와 `콘센트 필수`는 같은 조건의 요구 수준만 바꾼다.
- 반경·지역·대상 변경: 변경한 필드 외의 의미 상태를 유지한다. `해운대로 바꿔`의 조사도 분리한다.
- undo: 직전 의미 변경 snapshot 하나만 복원한다. 설명·선택은 의미 조건 변경 이력을 추가하지 않는다.

## 6. 장소 참조 방식

결과 snapshot의 고정 순번과 `place_key`를 사용한다. Kakao 외부 ID는 검색어가 달라져도 같은 키가 되고 DB ID 및 기존 별칭도 제외 검사에 사용한다. 같은 장소를 새 검색어 ID로 다시 포함시키지 않는다.

설명·비교·정보 조회는 기존 결과를 대상으로 처리한다. 설명 대상은 이후 `그곳`의 선택 참조가 된다. 존재하지 않는 순번은 새 검색으로 해석하지 않는다. 설명은 저장된 근거·거리·주소와 확인되지 않은 항목을 구분하며 새로운 장소 사실을 만들지 않는다.

## 7. Clarification 상태 보존

추가 질문 중 기존 frame, 결과 snapshot, 선택, 순번·장소 참조를 유지한다. 질문 답변에 조건을 이어 적용한다. 결과 없는 설명 응답이나 공급자 실패 때문에 기존 참조를 삭제하지 않는다. 새 대화/명시적 reset에서만 검색 상태·결과·변경 이력을 초기화한다.

## 8. 늦은 응답 방지

웹·모바일에서 대화 generation과 세션 ID를 검사한다. 이전 세션 생성·turn·지도 후보 응답이 새 대화를 덮지 못하도록 한다. 웹의 비동기 정리도 자신의 generation에서만 수행한다. 서버는 `expected_version` 불일치에 검색 실행 전 HTTP 409를 반환한다. 충돌 시 자동 새 세션·무상태 검색으로 바꾸지 않는다. 클라이언트가 보내는 legacy previous context는 서버 저장 상태를 덮지 못한다.

## 9. Kakao 누락 원인 및 개선

첫 페이지만 가져오거나 추가 페이지 실패 시 이미 가져온 후보까지 버리는 경로가 있었다. API가 제공하는 `meta.is_end`에 따라 제한된 추가 페이지를 읽고 외부 ID로 중복 제거한다. 후속 페이지 실패는 정상 페이지 결과를 보존하고 `partial`로 표시하며 첫 요청 실패는 오류로 전달한다. 지도 보충 검색에서도 먼저 얻은 문서를 보존한다. 대상별 검색 변형과 최초 후보 수집을 유지하면서 사용자 조건을 자동 완화하는 보충은 중단했다.

페이지 종료 정보와 파라미터 기준은 [Kakao Local 공식 문서](https://developers.kakao.com/docs/ko/local/dev-guide)를 사용했다. 공급자 색인 차이, 반환 한도 및 실제 속성 근거 부재까지 해결했다는 뜻은 아니다.

## 10. 단발 검색 평가

운영 일반 검색 8개를 검사했다: 서면 카페·약국·주차장, 해운대 카페, 서울역, 부산역, 스타벅스 서면, 메가커피 서면점. 모두 JSON HTTP 200이었다. 메가커피 서면점은 1건, 나머지는 요청 한도 10건을 반환했다. 이 검사는 연결·응답 검증이며 모든 장소의 실제 속성을 사람이 감사한 정확도 지표는 아니다.

로컬 Django recommendations 전체 988건: 실패 0, 제외 19건(실행 969건 통과). 웹 114건 통과와 production build 성공, 모바일 TypeScript·lint 통과. `git diff --check` 오류 없음. 고정 근거를 이용해 부정/부분 문자열, UNKNOWN/CONFLICTED, 선호조건, 공급자 페이지 실패를 추가 검증했다.

## 11. 연속 대화 평가

실행 가능한 60개 flow를 추가했다(지역 6 × 대상 2 × 필수조건 5). 실제 planner·patch·gate·세션·참조·undo 함수를 사용하되 장소 근거 및 공급자 응답은 고정 fixture를 사용한다. 60개 flow 모두 통과했다. 누적·제거·필수↔선호·교체 undo·설명 뒤 대명사 제외·원래 순번 비교·clarification 보존·평가 실패 뒤 undo는 별도 회귀 검사도 통과했다.

운영 공개 API 최종 23건: 정상 HTTP 200 22건, 의도한 stale version HTTP 409 1건. 필수조건 위반 0, 개발 디버그 노출 0, 의미 상태 기대값 불일치 0, 장소 참조/제외 불일치 0이었다.

운영 연속 흐름:

1. `서면 카페 → 주차 필수 → 더 가까운 데 → 콘센트도 필수 → 주차 조건 취소 → 1km 안으로 → 방금 변경 취소 → 2번은 왜 추천했어? → 해운대로 바꿔`.
2. 별도 세션에서 `서면 카페 → 첫 번째와 두 번째 비교 → 두 번째는 왜? → 그곳은 빼줘 → 다른 곳 보여줘`.

첫 흐름에서 주차 취소 후 콘센트만 유지한 2건을 반환했다. 1km로 좁히면 0건, undo하면 반경만 복원하고 같은 2건을 복원했다. 두 번째 흐름에서는 원래 두 장소를 비교하고 두 번째를 설명·제외한 뒤 다음 검색에서도 제외를 유지했다. AI 및 공급자 응답은 변동될 수 있어 이 표본의 통과를 전체 서비스 완전 정확도로 일반화하지 않는다.

증거 파일: `runtime/search-regression-final.txt`, `runtime/search-public-evaluation.json`, `runtime/search-public-references.json`. 토큰·자격 증명은 평가 파일에 기록하지 않았다.

## 12. 남은 검색 품질 문제와 배포 범위

- 주차·콘센트·조용함 등 실제 확인 근거가 적은 지역/대상은 결과가 0건일 수 있다. 미확인 후보를 채워 넣어 해결하지 않는다. 실제 데이터의 잘못된 업종·공급자 색인 차이도 별도 데이터 품질 과제다.
- 60개 flow는 재현 가능한 기능 회귀이며 60개 실제 운영 AI 대화가 아니다. 실제 운영 대화는 위 두 흐름을 검증했다.
- 모바일 수정은 새 APK 배포·실기기 OS/WebView/지도 SDK 검증까지 포함하지 않는다. 이번 운영 반영은 Django와 웹 검색에 필요한 선별 파일이다.
- FastAPI 전환, 대규모 재수집, 신규 AI Web Search는 실행하지 않았다.

### 운영 최종 상태 및 복구 기록

Django·gateway 모두 running/healthy. nginx 설정 검사 통과. 공개 홈 HTML 200, 검색 JSON 200, CORS 공개 주소 허용. 디스크 38G 중 26G 사용·12G 여유(69%). 마지막 수정 두 파일의 로컬·서버 SHA-256 일치를 확인했다.

원본 백업은 서버 `app/runtime/release-backup-20261006-search-quality/`, 환경 파일 백업은 `app/runtime/release-backup-20261006-public-search-host/`에 있다. 변경 전 이미지 ID와 파일 해시 기록도 보존했다. 배포 중 gateway의 기존 템플릿/locations 파일을 누락한 이미지에서 502가 발생해 이전 이미지로 즉시 복구했다. 기존 운영 Dockerfile을 복원하고 shared 복사만 추가한 최종 이미지로 다시 빌드·설정 검사·배포한 뒤 위 공개 검증을 완료했다.

같은 checkout에서 진행된 별도 UI 작업을 보존했으며 다수 파일을 일괄 커밋·업로드하지 않았다.
