# 데이터 정제 기준

## 1. 문서 목적

본 문서는 상황 기반 생활 장소 추천 지도 서비스에서 외부 데이터를 수집한 뒤, 추천 서비스에서 사용할 수 있도록 정제하는 기준을 정의합니다.

현재 프로젝트에서는 공공데이터 CSV, 자체 수집 JSON, 지도 API 검색 결과, 블로그 검색 결과 기반 후보 태그를 함께 검토하고 있습니다.

다만 모든 데이터를 같은 방식으로 저장하지 않습니다.

- 실제 장소 데이터는 `Place` 중심으로 정규화합니다.
- 장소의 추천 가치 정보는 `Tag`, `PlaceTag` 구조로 분리합니다.
- 원본 데이터는 삭제하지 않고 `raw` 또는 원본 파일로 보존합니다.
- 블로그 검색 결과 기반 정보는 확정 태그가 아니라 후보 태그로 관리합니다.
- 지도 API 검색 결과는 API 정책 확인 전까지 대량 저장 대상으로 확정하지 않습니다.

---

## 2. 원본 데이터 보관 원칙

원본 데이터는 수정하지 않고 별도로 보관합니다.

```txt
ExData/
├─ CSVData/
│  ├─ citypark/
│  ├─ freewifi/
│  ├─ smokearea/
│  ├─ toilet/
│  └─ parking/
└─ JsonData/
   ├─ smoke/
   ├─ tourism/
   └─ beach/
```

원본 데이터를 직접 수정하지 않는 이유는 다음과 같습니다.

- 원본 출처를 추적하기 위해
- 인코딩 문제를 방지하기 위해
- 좌표 소수점 손실을 방지하기 위해
- 모델 변경 시 다시 정제할 수 있도록 하기 위해
- 데이터 오류 발생 시 원본과 비교하기 위해

## 3. 데이터 사용 단계 구분

수집 데이터는 다음 단계로 구분합니다.

| 단계 | 설명 | 예시 |
|---|---|---|
| raw | 원본 데이터 | 공공데이터 CSV, 수집 JSON |
| normalized | 공통 장소 구조로 정제한 데이터 | 흡연구역 normalized JSON |
| fixture | Django DB에 넣기 위한 데이터 | 카페 태그 fixture |
| candidate_tag | 확정 전 후보 태그 | 블로그 기반 관광지 태그 후보 |
| runtime_candidate | 추천 시점에만 사용하는 외부 후보 | 지도 API 검색 결과 |

현재 흡연구역은 DB 조회 방식으로 전환되었고, 카페 태그는 Django fixture 형태로 준비되어 있습니다.
관광지 블로그 태그는 후보 태그 생성 단계이며, 확정 태그로 바로 사용하지 않습니다.

## 4. 공통 Place 정제 기준

모든 장소 데이터는 최종적으로 아래 기준을 적용합니다.

| 항목 | 기준 |
|---|---|
| 장소명 | 장소명이 없는 데이터는 1차 import 또는 fixture 대상에서 제외합니다. |
| 카테고리 | 서비스에서 사용하는 표준 카테고리로 매핑합니다. |
| 위도 | 숫자로 변환 가능한 값만 사용합니다. |
| 경도 | 숫자로 변환 가능한 값만 사용합니다. |
| 좌표 범위 | 대한민국 범위에서 벗어난 좌표는 제외합니다. |
| 주소 | 도로명 주소 또는 지번 주소 중 하나 이상 있으면 저장합니다. |
| 데이터 기준일 | 원본 데이터에 기준일이 있으면 저장합니다. |
| 원본 데이터 | 정제 후에도 `raw`에 원본 행 정보를 저장합니다. |
| 중복 | 장소명, 주소, 좌표를 기준으로 중복 여부를 판단합니다. |

---

## 5. 좌표 정제 기준

지도 표시와 거리 계산을 위해 위도와 경도는 핵심값으로 사용합니다.

| 상태 | 처리 방식 |
|---|---|
| 위도/경도 모두 있음 | import 또는 fixture 대상 |
| 위도 또는 경도 하나만 있음 | import 제외 |
| 위도/경도 없음, 주소 있음 | 주소 변환 후보로 보류 |
| 위도/경도 없음, 주소도 없음 | 제외 |
| 대한민국 범위 밖 좌표 | 제외 |

대한민국 좌표 범위는 1차적으로 아래 기준을 사용합니다.

```txt
위도: 33 ~ 39
경도: 124 ~ 132
```

## 6. 중복 데이터 판단 기준

중복 데이터는 다음 기준을 조합하여 판단합니다.

| 기준 | 설명 |
|---|---|
| 장소명 | 공백 제거 후 비교 |
| 주소 | 도로명 주소 또는 지번 주소 비교 |
| 좌표 | 위도/경도 소수점 일정 자리까지 비교 |
| 카테고리 | 같은 카테고리 내 중복 우선 판단 |
| source_file | 같은 파일 내 중복 여부 확인 |

초기 구현에서는 무리하게 모든 중복을 제거하지 않고, 명확히 같은 데이터만 제외합니다.

## 7. 데이터별 사용 컬럼과 처리 기준

### 7.1 공중화장실

| 사용 목적 | 원본 컬럼 |
|---|---|
| 장소명 | 화장실명 |
| 카테고리 | 공중화장실 고정 |
| 지번 주소 | 소재지지번주소 |
| 도로명 주소 | 소재지도로명주소 |
| 위도 | WGS84위도 |
| 경도 | WGS84경도 |
| 개방 시간 | 개방시간, 개방시간상세 |
| 장애인 편의 | 장애인용 대변기/소변기 수 |
| 어린이 이용 | 어린이용 대변기 수 |
| 비상벨 | 비상벨설치여부 |
| CCTV | 화장실입구CCTV설치유무 |
| 관리기관 | 관리기관명 |
| 기준일 | 데이터기준일자 |

#### 처리 기준

- 좌표가 있는 데이터만 1차 import 후보로 사용합니다.
- 좌표가 없고 주소가 있는 데이터는 추후 주소 변환 후보로 분리합니다.
- 장애인용 또는 어린이용 시설 수가 1 이상이면 관련 태그 후보를 부여할 수 있습니다.
- 개방시간에 24시간이 포함된 경우 `24시간` 태그를 부여할 수 있습니다.

- 설치시설구분명과 설치장소명을 활용하여 보조 태그를 부여할 수 있습니다.
- 단, `노트북 작업 가능`, `조용함`, `콘센트 있음`은 무료 와이파이 데이터만으로 확정하지 않습니다.

### 7.4 흡연구역

흡연구역 데이터는 현재 DB 조회 기반 추천으로 전환된 상태입니다.

| 사용 목적 | 가능한 원본 컬럼 |
|---|---|
| 장소명 | 시설명, 설치위치, 장소명 등 |
| 카테고리 | 흡연구역 고정 |
| 주소 | 주소, 도로명주소, 지번주소 등 |
| 위도 | 위도, latitude 등 |
| 경도 | 경도, longitude 등 |
| 시설 형태 | 시설형태, 흡연실형태 등 |
| 관리 여부 | 관리여부 |
| 기준일 | 데이터기준일자 |

#### 처리 기준

- 좌표가 있는 데이터부터 우선 import합니다.
- 통계성 데이터는 장소 데이터로 사용하지 않습니다.
- `흡연`, `흡연구역` 태그는 기본 부여합니다.
- 실내, 실외, 개방형, 폐쇄형 정보가 명확한 경우에만 관련 태그를 부여합니다.
- 원본 행 정보는 `raw` 필드에 보존합니다.

### 7.5 주차장

| 사용 목적 | 가능한 원본 컬럼 |
|---|---|
| 장소명 | 주차장명 |
| 카테고리 | 주차장 고정 |
| 주소 | 소재지도로명주소, 소재지지번주소 |
| 위도 | 위도, WGS84위도 |
| 경도 | 경도, WGS84경도 |
| 주차장 구분 | 노상/노외/부설 등 |
| 운영 시간 | 평일/토요일/공휴일 운영시간 |
| 요금 정보 | 유료/무료, 기본요금, 추가요금 |
| 관리기관 | 관리기관명 |
| 기준일 | 데이터기준일자 |

#### 처리 기준

- 좌표가 있는 데이터는 1차 import 후보로 사용합니다.
- 운영시간, 요금, 주차장 구분은 사용자 검색과 추천 이유에 활용 가능한 정제 필드로 분리합니다.
- `무료`, `유료`, `공영`, `야간 이용 가능 후보` 등은 원본 컬럼이 명확할 때만 부여합니다.
- 실시간 주차 가능 대수는 초기 구현 범위에 포함하지 않습니다.

---

### 7.6 카페 태그 데이터

카페의 장소 정보와 추천 가치 태그는 공공데이터만으로 확보하기 어렵기 때문에, 지도 API 검색 결과와 블로그 검색 결과를 조합해 후보를 수집했습니다.

#### 처리 기준

- 카페 후보는 상황 기반 검색어로 수집합니다.
- 예: 조용한 카페, 노트북 작업 가능한 카페, 감성 카페, 혼자 가기 좋은 카페
- 블로그 검색 결과 기반 태그는 확정 태그가 아니라 후보 태그로 관리합니다.
- 프랜차이즈 카페는 무조건 제외하지 않고, 공부/작업 장소로 활용 가능한 경우 후보로 남깁니다.
- 유명 저가형·테이크아웃 중심 브랜드는 추천 품질 저하 가능성이 있어 필터링 또는 주의 태그 대상으로 분리합니다.
- 현재 카페 태그 데이터는 Django fixture 형태로 준비되어 있습니다.

---

### 7.7 관광지/해수욕장 데이터

관광지와 해수욕장 데이터는 산책, 힐링, 전망, 야경, 드라이브 목적지 후보로 활용할 수 있습니다.

#### 처리 기준

- 장소명, 주소, 좌표, 카테고리를 우선 정제합니다.
- 관광지 소개나 분류값이 있으면 보조 태그 후보 생성에 활용합니다.
- 블로그 기반 태그는 `candidate` 상태로 관리합니다.
- `야경 보기 좋음`, `사진 찍기 좋음`, `힐링하기 좋음` 등은 블로그 검색 결과만으로 확정하지 않습니다.
- 관광지 태그 후보는 별도 JSON 결과 파일로 보관하고, 검수 후 fixture 또는 DB 저장 여부를 결정합니다.

## 8. import 제외 기준

다음 데이터는 초기 import 또는 fixture 변환에서 제외합니다.

| 제외 기준 | 설명 |
|---|---|
| 장소명 없음 | 사용자가 장소를 인식하기 어려움 |
| 위도/경도 없음 | 지도 표시와 거리 계산 불가 |
| 좌표 변환 실패 | 거리 계산 불가 |
| 대한민국 범위 밖 좌표 | 잘못된 좌표 가능성 |
| 통계성 데이터 | 장소 단위 데이터가 아님 |
| 출처 불명 데이터 | 사용 조건 확인 필요 |
| 중복이 명확한 데이터 | 동일 장소 반복 저장 방지 |
| 폐업/운영 종료 추정 데이터 | 추천 품질 저하 가능성 |

## 9. 정제 실패 데이터 처리

정제 실패 데이터는 바로 삭제하지 않고 로그 또는 skipped 결과로 남깁니다.

예시 로그 항목은 다음과 같습니다.

| 항목 | 설명 |
|---|---|
| source_file | 원본 파일명 |
| source_row_id | 원본 행 번호 |
| reason | 제외 사유 |
| raw | 원본 데이터 |

정제 실패 데이터는 추후 주소 보정, 컬럼 보정, 출처 확인 후 재처리할 수 있습니다.

## 10. 태그 자동 부여와의 연결

데이터 정제 이후 장소가 import되면, 해당 장소의 카테고리와 원본 컬럼 값을 기준으로 태그를 자동 부여합니다.

태그 부여 방식은 다음 문서에서 관리합니다.

```txt
docs/04_recommendation/tagging-rule.md
```

## 11. 현재 단계에서 주의할 작업

현재 프로젝트에서는 일부 데이터가 실제 DB 또는 fixture 단계까지 진행되었지만, 모든 데이터가 같은 수준으로 검증된 것은 아닙니다.

따라서 다음 사항을 주의합니다.

- fixture 생성 데이터와 후보 태그 JSON을 구분합니다.
- 후보 태그를 확정 태그처럼 표시하지 않습니다.
- 블로그 검색 결과 기반 태그는 검수 전까지 추천 점수에 약하게만 반영합니다.
- 지도 API 결과를 대량 저장하지 않습니다.
- 좌표 없는 데이터의 대량 지오코딩은 후순위로 둡니다.
- 중복 데이터 완전 제거는 초기 구현 범위를 넘어가므로 명확한 중복부터 처리합니다.
