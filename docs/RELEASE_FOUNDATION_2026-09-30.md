### 운영 반영 순서와 복구 기준

1. 서버에서 최신 백업 업로드와 별도 복원 결과, 디스크 여유, 현재 실행 이미지·환경 파일,
   Caddy 호스트 브리지 IP와 게이트웨이 컨테이너 IP를 확인한다. 기존 파일은 별도로 보관한다.
2. 두 IP를 정확한 단일 주소로 설정한다. 게이트웨이는 기존 사설 3000 포트를 유지하고
   공개 전용 3001 포트를 추가한다. Caddy의 공개 전달 대상을 3001로 전환한다.
   Spring의 공개 OAuth 기본 주소를 `https://yeogiljido.com`으로 설정한다.
3. 변경 전 설정 검사를 통과시킨 뒤 게이트웨이, Spring, Django, 웹을 필요한 범위만
   갱신한다. 공개·사설 상태 응답, 두 이용자의 요청 제한 분리, 위조 헤더 차단,
   공급자별 로그인과 앱 복귀, 정책·지원·삭제 페이지를 확인한다.
4. 실패하면 보관한 환경 파일과 이전 이미지로 해당 서비스를 되돌리고 Caddy 전달
   대상을 기존 3000으로 복구한다. 데이터베이스는 임의 초기화하거나 migration을
   역적용하지 않는다. 새 계정 삭제 기능에는 스키마 migration이 없다.

### 운영 반영 결과 (2026-09-30)

  `df` 재조회에서 38GB 파일시스템 중 14GB 여유(64~65% 사용)였다.
- 최신 `2026-09-29T073700Z` S3 덤프(469,630,905바이트)를 운영 DB와 네트워크가
  분리된 임시 PostGIS 컨테이너로 복원했다. 장소 1,257,991건, 장소 태그 근거
  377,754건과 PostGIS 3.4를 확인했고 서비스 종료 상태는 성공이다.
- `b232cd06` 브랜치를 승인받은 기존 GitHub 원격에 올렸다. 서버의 기준 파일과
  내용 비교 후 운영 코드 13개 파일만 교체했다. 원본 파일 묶음과 해시 목록은 서버의
  `/home/ubuntu/life-infra-map/release-backups/release-20260930T010421Z.*`에 있다.
  환경 파일은 보관 묶음에 포함하지 않았다.
- 게이트웨이·Spring·Django 이미지를 차례로 재빌드했다. Nginx 설정 검사,
  Django 시스템 검사, 3개 컨테이너 건강 상태가 통과했다. Caddy를 공개 3001
  포트로 재설정했고 사설 3000 포트도 200 응답을 유지한다.
- 공개 HTTPS에서 개인정보처리방침·지원·삭제 요청 페이지가 Chrome에서 열리고,
  지도 임베드가 Kakao 지도를 표시했다. 비인증 계정 삭제 POST는 401이다.
- 승인받은 일회용 계정을 만들어 공개 HTTPS 삭제 API에 접근했다. 응답은 204였고
  계정·댓글·문의 삭제, 공개 게시글 작성자 익명화를 DB에서 확인했다. 검증용 게시글은
  이후 정리했다. 기존 이용자 계정은 삭제하지 않았다.
- Google·Naver·Kakao 로그인 시작 요청은 각 공식 인증 호스트로 302 이동하며
  `https://yeogiljido.com/spring/api/login/oauth2/code/{공급자}`를 사용한다.
  테스트 계정으로 공급자 동의와 앱 복귀까지 완료한 것은 아니다.
- 공개 포트에서 시험 주소 1의 21번째 로그인 갱신 요청은 429, 별도 주소의
  첫 요청은 401이었다. 사설 포트에서는 전달 헤더를 21개 다른 주소로 위조해도
  21번째가 429였다. 이 시험은 서버 내부 연결에서 수행했다.
