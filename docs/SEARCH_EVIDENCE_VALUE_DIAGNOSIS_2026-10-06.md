# 검색 근거의 실제 검색 가치 진단

기준: 2026-10-06 운영 Django 설정·PostgreSQL 읽기 전용 집계, 현재 저장소 코드, 같은 날 보관된 공개 검색 평가 18건. 운영 설정과 DB는 SSM을 통해 실행 중인 Django 컨테이너에서 직접 조회했다. 배포, 설정 변경, DB 쓰기, 신규 검색 요청은 하지 않았다. 수치는 이 시점의 스냅샷이다.

## 1. 가장 큰 병목 TOP 3

1. **근거의 검색 가능 상태 전환과 조건 조합 부족.** 부산 카페 13,362곳 중 유효한 긍정 Evidence에 `조용함+콘센트+노트북작업`이 함께 있는 곳은 20곳이다. 검색 코드가 확인 태그로 읽는 `PlaceTag` 기준 조합은 0곳이다. 서울 카페는 각각 3곳과 0곳이다. 원본 근거 수와 엄격 조건 검색에서 사용 가능한 장소 수 사이에 큰 간격이 있다.
2. **수집의 장소 귀속 실패와 낮은 유효 산출.** 최근 14일 수집 작업 84,000건 중 `IDENTITY_MISMATCH`가 55,457건(66.0%)이다. 181,080회 요청에서 새 네이버 Evidence 25,642건(요청 대비 14.2%), 작업 통계상 새 활성 Evidence 3,559건(2.0%)이 나왔다. 새 네이버 Evidence 중 현재 유효·긍정·승인인 것은 2,777건(10.8%)이다. 각각 다른 분모와 판정이므로 동일한 전환율로 해석하지 않는다.
3. **검색 단계별 성과 관측의 공백.** 오늘 보관된 공개 API 평가 18건은 HTTP·최종 건수·조건 위반 여부를 기록하지만 후보별 `DB/Kakao → Place identity → Evidence join → hard gate → score → rank`를 보존하지 않는다. Retrieval·identity join·ranking 가운데 무엇이 몇 건을 잃게 하는지는 현재 자료로 분리할 수 없다. Ranking이 3위라는 뜻이 아니라, 다음 결정을 막는 관측 병목이다.

### 운영 AI 실제 상태와 한 검색의 경로

| 설정 | 운영값 |
| --- | --- |
| `AI_PROVIDER` | `rule` |
| `CONVERSATIONAL_SEARCH_AI_ENABLED` / `AI_RERANK_ENABLED` | `false` / `false` |
| `AI_INTENT_MODEL` / `AI_RERANK_MODEL` | `gpt-5-mini` / `gpt-5-nano` (설정 문자열; 운영 호출 증거 아님) |
| `AI_WEB_SEARCH_ENABLED` / `AI_WEB_SEARCH_PROVIDER` | `false` / `naver_search` |
| `SEMANTIC_RETRIEVAL_ENABLED` / `SEMANTIC_CANDIDATE_INJECTION_ENABLED` | `false` / `false` |
| hybrid 가중치 | condition .20, tag .10, semantic .35, distance .10, evidence .10, freshness .05, reliability .10 |

현재 Intent는 로컬 규칙/대화 patch 경로가 가능하고, Retrieval은 DB와 Kakao를 병렬 수집한다. Evidence는 DB 후보의 `PlaceTag`와 장소 Evidence 품질 프로필을 읽는다. AI reranker, AI Web Search, semantic 후보 주입은 위 운영값으로 비활성이다. 최종 필수조건 gate와 품질·근거·거리 정렬은 실행된다. `_hybrid_score()`의 가중치는 **AI reranker가 성공한 경로의 계산식**이므로 현재 운영 순위를 설명하는 값으로 쓰면 안 된다.

확인 `PlaceTag`는 `is_verified` 또는 `checked/user_verified`의 `confirmed` 상태를 셌다. 코드가 과거 자료 태그를 추가로 배제하므로 이 수치는 실제 검색 가능량의 **상한에 가깝다**. 부산 카페에서 확인 `PlaceTag`가 있는 고유 장소는 14개 핵심 조건 기준 139곳, 서울은 23곳이다. 각각 전체 카페의 약 1.04%, 0.06%이다. 부산의 개별 확인 태그는 조용함 33, 콘센트 38, 노트북 30, 분위기 51, 전망 18곳; 서울은 각각 1, 3, 7, 2, 0곳이다.

웹 Evidence 2개가 독립적이어도 `aggregate_tag_evidence()`는 이를 `candidate`로 유지한다. 공식 양성 필드, 관리자 확인+웹 근거, 사용자 검증+웹 근거 등 명시된 경로에서만 확인 태그가 된다. 따라서 원본 근거가 누적돼도 확인 검색 결과가 선형으로 늘지 않는 것은 현재 정책상 예상되는 현상이다. 이 정책의 안전 기준은 유지하되, 독립성·정확한 장소 귀속·유효기간을 검토할 수 있는 승격 흐름을 개선해야 한다.

## 3. 태그 편중과 현재 수집 효율

운영 전체는 장소 1,257,993곳, Evidence 391,455건, Tag 190개다. Evidence의 주요 출처는 `field_rule` 191,034, `external_data` 128,141, `naver_blog_search` 69,479건이다. 총량 상위는 업종/기본 시설 태그에 크게 치우친다. 최근 14일 새 Evidence 1위는 `혼밥좋음` 14,602건이고 `콘센트있음`은 394, `혼자이용좋음`은 47, `단체석있음`은 20건이다. **검색 가치가 높은 조합의 증가가 총량 증가를 따라가지 못한다**는 가설을 부산·서울 카페 조합 수치가 지지한다. 단, 사용자 검색 로그의 최근 74건에는 구조화 요청 조건이 없어 태그별 실제 검색 빈도 순위는 산출할 수 없다.

최근 14일 수집 작업 84,000건은 고유 장소도 84,000곳이다. 같은 장소의 반복 작업률은 이 기간 **0%**다. 반면 새 네이버 Evidence 25,642건은 10,992개 장소와 16,243개 장소·태그 조합에 분포한다. 5,045개 조합에 2건 이상 쌓였고 조합당 첫 1건을 제외한 9,399건(36.7%)은 같은 장소·태그의 추가 근거다. 이것을 곧바로 중복 저장 오류라 부를 수는 없다. 서로 독립적인 근거가 승격에 필요할 수 있다. 기존 충분 근거 장소 재수집률, 원문 URL 중복 반려율, 신규 장소·조건 순증은 현재 집계에서 분리되지 않았다.

작업 종료 원인은 `IDENTITY_MISMATCH` 55,457, `NO_TAG_EXPRESSION` 14,651, `NO_SEARCH_RESULT` 2,813, `INSUFFICIENT_SNIPPET` 87건이다. 작업 통계의 진단 카운터에는 검색 결과 618,531, identity match 63,678, 태그 표현 25,642가 있다. 이 카운터는 항목/시도 수와 작업 수가 섞여 있으므로 하나의 identity match rate로 나누지 않는다. 본문·인용 mismatch와 duplicate rejection의 독립 카운터는 확인하지 못했다. 최근 7일 새 Evidence는 13,701건(네이버 13,660), 수집 작업은 42,000건이다.

## 4. Evidence가 검색에 쓰이는 정도와 실패 원인 분류

현재 코드 흐름은 `Intent → DB/Kakao 후보 → DB PlaceTag·Evidence 품질 → 필수조건 gate → 품질 우선 정렬`이다. DB 후보는 기본적으로 가까운 장소를 제한된 창에서 가져오고 확인 필수 태그 장소를 추가 수집한다. Kakao 후보는 동일 이름+동일 주소 또는 30m 이내 좌표일 때 중복 병합한다. 별도의 전역 Kakao→내부 Place identity 조회 성공률은 기록되지 않는다. 현재 웹 후보 병합도 기존 후보 목록과의 중복 결합에 의존하므로, **후보 목록에 없던 내부 Place를 주소/ID로 찾아 Evidence를 붙이는 경로는 별도 설계가 필요하다.**

오늘의 공개 평가 18건 중 8건은 단발 검색 연결 검사, 9건은 대화 흐름 단계, 1건은 의도한 version 409다. 단발 8건은 모두 HTTP 200이며 7건 10개·1건 1개 결과였다. 대화 흐름에서 `주차 필수` 0건, `콘센트도 필수` 0건, `주차 조건 취소` 2건, `1km 안으로` 0건, undo 2건이었다. 이 표본은 대화 상태·엄격 조건 동작의 증거이지, 후보별 Evidence 사용률이나 정확도 표본은 아니다.

| 실패 분류 | 이번에 확인한 것 | 비율 판정 |
| --- | --- | --- |
| A. Evidence coverage | 위 지역·업종·조건 조합의 극소량 또는 0 | 부산·서울 카페 조합은 계량 완료 |
| B. Retrieval | 확인 태그 추가 수집 경로 존재, 실제 후보 누락 표본은 미추적 | 산출 불가 |
| C. Identity/Evidence join | 수집 작업의 장소 mismatch 55,457건; 검색 Kakao join은 별도 미계측 | 수집 비율 66.0%, 검색 비율 산출 불가 |
| D. Ranking | 최종 정렬은 조건·Evidence 품질을 앞세움; 후보별 역전 표본 없음 | 산출 불가 |
| E. Intent/conversation | 오늘 운영 대화 2개 흐름의 정책·참조 검증 완료 | 실패율 산출 불가 |

후보 pool의 내부 Evidence 장소 비율, Top 5 비율, strong 평균 rank/Top 5 밖 비율, 무근거가 확인 후보를 앞선 사례, Kakao identity 성공률은 **현재 데이터로 계산하지 못했다**. 이를 10~20개 대표 쿼리에서 내부 진단 기록으로 측정하는 것이 P0다. 개인 검색 문장·원문 인용·토큰은 기록하지 않고 쿼리 유형/태그와 후보 ID 해시·단계 카운터·점수 분해만 보관한다.

## 5. Ranking 문제 여부

현재 운영 AI reranker가 꺼져 `_hybrid_score()`는 실행 경로의 주 점수가 아니다. 기본식만 놓고 보면 semantic 35%, Evidence 10%이며 strong(90)과 weak(35)의 차이는 다른 조건이 같을 때 5.5점이다. 이는 **AI reranker를 켰을 때의 가상 비교**이고 현재 후보의 실제 점수 분해가 아니다. 게다가 최종 정렬은 `result_quality_sort_key → 조건 충족 수 → Evidence 품질 → 거리 → Evidence 강도 → 기타 점수` 순이라 가중치만으로 최종 역전을 단정할 수 없다.

필수조건은 마지막 gate에서 미확인 후보를 기본 결과에서 제외한다. `Tier 1 전 필수조건 확인 → Tier 2 일부 확인 → Tier 3 미확인`을 도입한다면 기본 결과에는 Tier 1만 두고 Tier 2/3는 사용자가 명시적으로 미확인 탐색을 선택했을 때만 보여야 한다. 현재 정책과 일부 품질 우선 정렬이 이미 이 원칙을 구현하므로, 큰 점수 가중치 변경보다 실제 후보 추적으로 역전 사례가 있는지 확인하는 것이 먼저다.

## 6. 실시간 AI Web Search 도입 효과 예상

운영 `AI_WEB_SEARCH_ENABLED=false`다. 코드의 `naver_search` 제공자 설정 문자열은 실시간 AI Web Search 활성 증거가 아니다. 현재 `AI_WEB_SEARCH_MAX_CANDIDATES=1`, 웹 쿼리 상한 기본 2, 웹 응답 캐시 600초다. 제안한 3~5개 후보 흐름은 코드·정책 변경이 필요하다.

기대 효과는 **빈 후보 발견**에 한정해 파일럿으로 검증한다. 현재 확인 근거 조합이 0인 검색에서 AI가 장소를 새로 찾아도 내부 Place와 정확히 매칭되고 필요한 확인 태그가 있어야 엄격 결과에 들어간다. 확인 근거가 없는 신규 장소는 `미확인 탐색 후보`로만 표시한다. 따라서 Coverage 자체가 0인 `조용함+콘센트+노트북`의 기본 결과를 웹검색만으로 채울 수는 없다. 현재 수집의 identity mismatch 규모를 고려하면 매칭 구현·정확도가 효과의 선행 조건이다.

## 7. 추천 호출 정책

권장 파일럿 정책: 필수조건을 만족하는 확인 후보가 3개 이상이면 웹검색 생략, 0~1개면 사용자에게 지연을 알리고 백그라운드로 웹검색 1회, 2개면 우선 기본 결과만 제공하고 확장 행동에서 호출한다. 한 번에 웹 쿼리 1개, 후보 최대 3개부터 시작하고 조건·지역 정규화 키의 짧은 캐시 및 장소+조건 조사 캐시를 둔다. 전체 Evidence를 프롬프트에 넣지 않는다. 웹 후보의 장소명·주소·외부 ID만 받아 내부 Place identity를 찾고, 매칭된 장소의 관련 태그·근거 최대 소수 건만 조회해 최종 gate에 넘긴다. 제한 시간·호출량·비용 상한은 파일럿의 p95 지연과 실제 Top 5 추가 기여율을 본 뒤 확정한다. 웹 실패 시 기존 검색은 그대로 완료한다.

배치 Naver/Codex 수집은 Evidence DB의 빈 조건 조합을 넓히는 역할, 실시간 웹검색은 현재 요청의 후보 발견 역할이다. `0건/확인 후보 부족 → 지역×업종×필수조건 결핍`을 익명 집계해 다음 배치 큐의 우선순위로 보내되, 이미 충분한 장소·태그는 감점한다. 배치 조사 결과의 정확한 장소 귀속·검토·유효기간을 통과해야 검색 확인 상태로 승격한다.

## 8. FastAPI 판단

| 안 | 이동 범위와 데이터 소유 | 운영 비용/판단 |
| --- | --- | --- |
| A. Spring + Django 유지 | 기존 Place/Tag/Evidence, ORM, PostGIS, migration, Admin, 수집 명령, conversation session, orchestrator 그대로 | **추천.** 이번 병목은 데이터 귀속·확인 전환·관측이며 프레임워크를 바꿔도 줄지 않는다. 네트워크 hop·이중 DB 접근 추가 없음. |
| B. Spring + Django(Data/Admin/Migration) + FastAPI(Search/AI) | 검색 planner·orchestrator·session 경계와 검색 API 이동. Django ORM 의존을 분리하거나 서비스 호출/새 DB repository가 필요. PostGIS 쿼리·트랜잭션·session 소유권·테스트를 재구성 | 이후 p95 지연 또는 배포 독립성이 **실측 병목**일 때만 검토. 서비스 간 hop과 양쪽 관측·배포가 늘어난다. Migration/Admin 소유는 Django에 둔다. |
| C. Spring + FastAPI, Django 제거 | 모델·migration·Admin·수집/정제 명령·ORM/PostGIS·session·테스트 모두 이전 | 현재 근거 없음. 전환 비용과 데이터 소유 위험이 가장 크다. |

현재 Django 검색 orchestrator가 직접 Django 설정, ORM/Place·PlaceTag, PostGIS 분기, 캐시, 대화 세션을 사용한다. FastAPI의 일반적 속도 인상만으로 B/C를 택할 수 없다.

B에서 옮길 파일군은 최소 `backend/recommendations/views.py`의 검색 API, `services/ai_search_orchestrator.py`, `ai_intent_planner.py`, `ai_candidate_reranker.py`, `conversation_sessions.py`와 관련 테스트다. `models.py`, `migrations/`, `admin.py`, 수집 management command는 Django 소유로 남고 FastAPI 검색은 Django 서비스 API를 호출하거나 독립 DB repository를 구현해야 한다. C는 남겨 둔 영역까지 모두 이전해야 한다. B/C 모두 PostGIS 거리 쿼리의 일치성, session 동시성, 양쪽 배포·로그 연결, 네트워크 hop 지연을 새로 검증해야 한다.

## 9. 모니터링안

기존 일일 리포트와 컨테이너 상태 확인을 활용해 먼저 단계별 구조화 메트릭을 저장한다. 시스템은 CPU/RAM, DB 연결·느린 쿼리, API p50/p95/p99, 5xx와 공급자 실패를 관측한다. 검색 요청마다 Intent, DB/Kakao retrieval, Evidence join, AI Web Search, reranker, final gate 지연과 후보 수를 기록한다. 품질은 확인/미확인 후보 수, identity match·Evidence join 성공률, 필수조건 충족률, 조건 완화 요청률, 0건률, 확인 후보 Top 5 비율, 웹 발동률, 웹으로 **실제 Top 5에 추가된 확인 후보** 비율을 집계한다. 개인정보·원문·비밀값은 메트릭 라벨에 넣지 않는다.

현 인프라에서는 앱 구조화 로그+기존 일일 리포트와 CloudWatch 경보를 먼저 연결한다. Prometheus/Grafana/Loki는 메트릭 양, 보존/탐색 요구, CloudWatch 비용을 실제로 본 뒤 도입한다. 우선순위는 대시보드 제품보다 후보 단계별 데이터가 빠짐없이 남는 것이다.

## 10. P0/P1/P2 계획

- **P0:** 10~20개 고정 검색 표본에 후보 ID별 단계 카운터·identity·Evidence join·hard gate·점수 분해·최종 rank를 내부 진단으로 기록한다. 부산/서울 `지역×업종×조건` 조합, 확인 `PlaceTag` 전환률, 수집 miss reason을 같은 날짜의 대시보드로 묶는다. 수집 `IDENTITY_MISMATCH` 상위 원인을 주소/이름/좌표 유형별 집계로 나누고 원문 공개 없이 검증한다.
- **P1:** 검색 결핍 조합을 배치 수집 우선순위에 연결하고, 정확한 장소 귀속·독립 출처·유효 기간을 충족한 Evidence의 확인 전환 흐름을 개선한다. Kakao/웹 후보의 내부 Place identity 조회를 후보 병합과 분리해 정확도 평가를 한다. 확인 후보 부족 검색에서만 1쿼리·3후보 실시간 AI Web Search를 작은 비율로 파일럿하고 지연·비용·Top 5 기여를 비교한다.
- **P2:** 후보별 실측 역전 사례가 있을 때만 ranking tier·점수식을 조정한다. FastAPI 분리는 p95 지연/독립 배포 이득이 전환 비용을 넘는다는 측정이 나온 뒤 재평가한다. 관측 규모가 커질 때 Prometheus/Grafana/Loki 도입 여부를 결정한다.

### 이번 진단의 한계

검색 요청 10~20개의 전체 후보 trace가 저장돼 있지 않아 B/C/D/E 실패 비율 및 실제 score breakdown은 제시할 수 없다. 사용자 로그 최근 74건의 조건 배열이 비어 있어 `많이 검색되지만 coverage 낮은 태그`의 **수요 기준** 순위도 낼 수 없다. 수집의 원문 URL 중복 반려·본문 인용 불일치·기존 충분 근거 재조사율은 현재 통계에서 분리되지 않았다. 작업 통계 원문 3건의 조회는 자동 승인 심사가 민감 정보 가능성을 이유로 거절했다. 원문 대신 숫자만 운영 서버에서 집계했다.
