# 프로젝트 진행 방향

## 0. 서비스 방향 기준 정리

### 0.1 서비스 방향

- 기존의 “상황 기반 생활 장소 추천 지도 서비스” 방향을 유지한다.
- 서비스의 핵심은 기존 지도 서비스처럼 장소명을 단순 검색하는 것이 아니라, 여러 출처의 장소 데이터를 카테고리와 태그로 분류하고 사용자의 상황에 맞게 추천하는 것이다.
- 지도는 추천 결과와 장소 정보를 확인하는 핵심 인터페이스로 사용한다.
- 팀원 정리안에서 나온 자연어 검색, 후기 기반 추정 태그, 추천 이유 생성 기능은 기존 기획을 대체하지 않고 확장 기능으로 흡수한다.

### 0.2 데이터 활용 기준

- 공공데이터, CSV, API, 팀 시드 데이터를 중심으로 실제 확보 가능한 장소 데이터를 우선 사용한다.
- 지도 API는 장소 후보 조회, 좌표/주소 확인, 추천 결과 부족 시 외부 후보 표시, 지도 마커 표시 등 보조 수단으로 활용한다.
- 블로그 검색 결과는 본문 전체를 무단 수집하는 방식이 아니라, 검색 결과의 제목, 요약, 작성일, URL 기반 후보 태그 생성에 활용한다.
- 블로그 기반 태그는 확정 정보가 아니라 “후기 기반 추정 태그” 또는 `candidate` 태그로 구분한다.
- 카페의 조용함, 콘센트 있음, 와이파이 있음, 노트북 작업 가능 여부는 공공데이터만으로 확정하기 어려우므로 후보 태그와 검증 태그를 구분한다.

### 0.3 추천 구조 기준

- 사용자의 자연어 입력 또는 빠른 선택 조건을 카테고리/태그 조건으로 변환한다.
- 초기 추천은 복잡한 머신러닝이 아니라 규칙 기반 점수 계산으로 구현한다.
- 추천 점수는 카테고리 일치, 태그 일치, 거리, 최신성, 신뢰도, 오류 제보 감점 등을 조합한다.
- AI는 실제 장소 정보를 임의 생성하지 않고, 자연어 입력을 추천 조건으로 변환하거나 후보 태그와 추천 이유를 생성하는 보조 역할로 사용한다.

## 1. 현재 완료한 작업

### 1.1 기획/문서

- 서비스 방향을 “상황 기반 생활 장소 추천 지도 서비스”로 재정리했다.
- 단순 지도 조회가 아니라 위치와 상황 기반 장소 추천을 서비스 중심으로 정의했다.
- 데이터 수집 단계와 서비스 기능 설계 단계를 구분했다.
- 지도 API 결과를 대량 저장하는 방식은 보류하고, 실시간 후보 조회와 지도 표시 중심으로 활용하기로 했다.
- 태그 출처, 상태, 신뢰도, 검증 여부를 관리하는 태그 전략 문서를 작성했다.

### 1.2 백엔드

- Django + Django REST Framework 기반 백엔드 구조를 생성했다.
- CORS 설정과 기본 API 연결을 완료했다.
- 추천 목업 API를 작성하고 Vue 프론트엔드와 연결했다.
- 카카오 로컬 API 검색 결과를 추천 응답 구조로 변환하는 흐름을 테스트했다.
- 흡연구역 추천 기능을 JSON 직접 조회 방식에서 DB 조회 방식으로 변경했다.
- `Place`, `Tag`, `PlaceTag` 구조를 기준으로 흡연구역 데이터와 태그를 연결했다.
- 추천 응답에 거리, 태그, 데이터 품질 점수, 출처 정보를 포함하도록 개선했다.
- 카페 태그 데이터를 Django fixture 형태로 추가했다.

### 1.3 프론트엔드

- Vue 기반 추천 테스트 화면을 구성했다.
- axios를 통해 백엔드 추천 API 응답을 받아 카드 형태로 표시했다.
- 카카오 JavaScript SDK를 연결해 지도 화면을 표시했다.
- 브라우저 현재 위치를 가져와 추천 API에 위도와 경도를 전달하는 흐름을 테스트했다.
- 추천 결과의 위도와 경도를 기반으로 지도 마커를 표시했다.
- 추천 카드에서 태그, 거리, 추천 이유, 출처 정보가 더 잘 보이도록 수정했다.

### 1.4 데이터 수집/태그 후보 생성

- 흡연구역 데이터를 수집하고 raw/normalized JSON 파일로 정리했다.
- 흡연구역 JSON 데이터를 `ExData/JsonData/smoke/` 하위로 정리했다.
- 공중화장실, 무료 와이파이, 도시공원, 주차장, 관광지, 해수욕장 데이터를 수집 후보 또는 실제 파일로 관리했다.
- 네이버 블로그 검색 API를 활용해 장소 관련 블로그 검색 결과 수집 테스트를 진행했다.
- 부산 카페 후보를 대상으로 상황 기반 태그 수집을 진행했다.
- 카페 태그 수집 결과를 하위 지역별로 확장했다.
- 카페 태그 데이터를 Django fixture 형태로 준비했다.
- 부산 관광지 데이터를 대상으로 블로그 기반 태그 후보 생성 스크립트와 결과 JSON을 추가했다.

## 2. 다음 작업 우선순위

### 2.1 Must

1. 수집 데이터와 fixture 로드 결과 확인
2. 카페 fixture와 흡연구역 DB 데이터가 같은 추천 응답 구조로 반환되는지 확인
3. 추천 카드에서 태그, 추천 이유, 출처, 거리 정보 표시 검증
4. 관광지 블로그 기반 후보 태그를 실제 추천에 반영할지 여부 결정
5. 발표/README용 데이터 확보 과정 정리

### 2.2 Should

1. 카페 태그 후보 중 저장 태그와 제외 태그 기준 정리
2. 관광지 태그 후보의 과도한 키워드 제거
3. 추천 점수에서 `confirmed`, `candidate`, `needs_verification` 태그 반영 비율 정리
4. 추천 결과 부족 시 지도 API 후보를 함께 보여주는 흐름 정리
5. 관리자 검수 전 후보 태그 표시 방식 정리

### 2.3 Could

1. 자연어 상황 검색 입력을 태그 조건으로 변환
2. AI 기반 추천 이유 생성
3. 후기/블로그 기반 후보 태그 요약
4. 사용자 저장, 오류 제보, 검증 기능
5. 드라이브/야경/힐링 추천 시나리오 고도화

## 4. 발표/문서화에 강조할 내용

- 문제 정의: 기존 지도 검색은 장소명 검색에는 강하지만 “지금 내 상황에 맞는 장소”를 고르는 데는 한계가 있다.
- 해결 방향: 위치, 상황, 카테고리, 태그, 거리, 출처, 신뢰도를 조합해 추천한다.
- 데이터 전략: 공공데이터와 API 데이터는 실제 장소 후보 확보에 사용하고, 부족한 추천 가치 정보는 후보 태그로 보강한다.
- 추천 전략: 초기 구현은 규칙 기반 추천으로 완성 가능한 흐름을 우선한다.
- 신뢰도 전략: 블로그/AI 기반 태그는 확정 정보가 아니라 후보 정보로 분리한다.
- 구현 전략: 지도는 추천 결과를 확인하는 핵심 인터페이스이고, 추천 로직은 백엔드에서 관리한다.
